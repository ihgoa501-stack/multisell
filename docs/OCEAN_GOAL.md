# 凌镜海洋目标

> status: `active`
> owner_confirmed: `true`
> confirmed_on: 2026-07-11
> authority: 凌镜建设终点、湖泊拆分和完成判定的唯一入口

## Owner 已确认的建设方向

凌镜采用“海洋目标 → 完整湖泊 → 持续推进直到达成”的建设方式。

海洋目标是：

> **让 Owner 能依靠一个正常运转、可信、可控、可恢复的凌镜系统，完整完成跨境电商经营：从现实问题与机会进入，形成有证据的决策，经 Owner 审批后受控执行，追踪订单、履约、结算和最终利润，再把真实结果反馈给下一轮决策。**

目标用户、首个国家、消费者、需求场景、销售渠道、商品、预算和损失上限仍为 `unknown`，必须在对应湖泊开始前由 Owner 确认或用现实证据消除未知。海洋目标不自动继承任何历史提案的具体答案。

## 海洋完成条件

只有同时满足以下条件，海洋目标才可标记完成：

1. Owner 能稳定启动、登录和使用系统，核心数据可创建、读取、修改并在重启后保留。
2. 一条真实经营链从现实问题或机会开始，经过证据、决策、审批、受控执行、订单、履约、售后、结算、现金和最终利润，完整走到复盘。
3. 活跃链路中的真实事实有来源和观察时间；`mock`、stub、固定返回和 AI 推断不能冒充真实经营事实。
4. 关键正常路径和主要错误路径均完成实现、自动测试与人工验收；高风险动作具备身份、权限、审批、审计、幂等、失败可见和恢复能力。
5. 最终结果能按 `actual / quoted / estimated / unknown / mock / inferred` 区分，并能用可信凭证复算或对账。
6. Owner 能在界面中理解发生了什么、决定下一步，而不需要判断代码或架构。

代码量、页面数、Agent 数、测试数、构建通过、一次成交或一次盈利都不能单独证明海洋完成。

## 湖泊规则

湖泊是一次能够完整完成和验收的端到端单元，不是降低终点标准的借口。

每片湖必须包含：

- 一个明确的现实结果；
- 正常路径和主要错误路径；
- 必要的数据、权限、审批、审计和恢复边界；
- 自动验证、Owner 人工验收和证据等级；
- 通过、失败、未知和停止条件；
- 完成后通往下一片湖的明确关系。

当完整方案与不完整捷径的差异只属于当前湖泊的必要实现、测试、错误处理或边界时，完成完整方案。真正无关的相邻产品、平台扩张或长期迁移不自动进入当前湖泊。

## 当前第一片湖：系统可用性

目标：Owner 能在本地规定环境中连续两次完成：

```text
启动系统
-> 使用有效 Owner 账户登录
-> 进入选定的核心页面
-> 创建一条明确标记为 mock 的测试记录
-> 保存、重新读取并修改
-> 重启系统
-> 确认数据仍存在
```

完成条件：

- 上述路径连续成功两次；
- 失败时显示可行动的错误，而不是静默失败；
- 使用的是实际前端、后端和数据库，不以单元测试代替；
- 记录启动方式、环境、账户前置条件、验证时间和结果；
- 测试数据明确标记为 `mock`，不升级为商业证据。

当前核心页面在完成只读诊断后选择；选择标准是最能证明系统基础可用，且不要求先确定市场、商品或外部平台。

## 后续湖泊的候选顺序

以下是依赖顺序，不是未经验证的固定产品范围：

1. 系统可用性湖；
2. Owner 自用决策湖；
3. 真实数据与受控执行湖；
4. 订单、履约、售后与结算真相湖；
5. 最终利润、现金与反馈学习湖。

每片湖开始前，必须根据上一片湖的事实重新确认具体范围。平台、市场、商品或 Agent 数量不能自行获得优先级。

## 持续执行与停止边界

- 当前湖未通过时，优先诊断和修复阻塞，不用相邻功能掩盖失败。
- 遇到高成本、不可逆外部动作、真实资金、凭证、账号权限或 materially different 的产品方向时，必须由 Owner 决定。
- 验证失败必须记录真实失败；学习不能把失败改写成成功。
- 海洋未完成时持续推进下一片已确认的湖；没有已确认湖时，当前任务是消除阻止确认的关键未知。
