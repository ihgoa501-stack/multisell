# 经营闭环模型纠偏

> 日期：2026-07-12
> 状态：当前有效的 Owner 裁决
> 范围：经营实验、交易结果核验与工程闭环的定义
> 代码变更：无

## 结论

“候选市场 → 选择商品 → 小额销售 → 付款、签收、退货、结算和最终利润”不是经营闭环。它只是经营行动与交易结果的顺序描述；首尾完整、状态机终止或最终利润完成对账，都不能在工程上建立反馈闭环。

当前 `internal/domain/experiment/`、`/api/v1/experiments` 和 `/experiments` 的准确定位是 **经营事实核验案卷**。它可以关联对象、保存证据、阻止部分越级声明并核验交易结果，但不能据此证明经营行动产生了订单、某个变量导致利润变化，或系统知道下一步应改变什么。

## 为什么原模型不成立

工程意义上的反馈循环至少需要：

1. 明确目标和允许偏差；
2. 可执行、可冻结、可识别的经营变量；
3. 经营动作真实作用于目标市场；
4. 能归属到该动作的可靠观测；
5. 实际结果与目标之间的偏差判断；
6. 将偏差转换为下一步动作的明确规则；
7. 下一步动作真实执行并再次获得观测。

现有模型主要实现对象关联、证据状态、顺序闸门和交易终局。它缺少上述完整控制结构。尤其是：

- `experiment_id` 只能证明记录被关联，不能证明因果；
- 付款、签收、退货和利润是结果观测，不是反馈规则；
- `stop / switch / adjust / continue` 标签只是决定记录，不证明下一步已执行；
- 完成一次交易不能说明为什么成功或失败，也不能说明下一次该改变什么；
- 状态机走到 `completed` 只表示流程终止，不表示反馈闭合。

## 事实等级

| 声明 | 等级 |
|---|---|
| `experiment` 模块、API、页面、状态、证据和对象关联存在 | `implemented` |
| 已有部分自动测试验证闸门和关联行为 | `automated_verified`（沿用既有审计范围） |
| 模块能够形成经营事实案卷 | `implemented`；真实使用价值仍为 `unknown` |
| 模块能够证明经营行动与订单、利润之间的因果关系 | 不成立 |
| 模块已经实现经营反馈循环 | `not implemented` |
| 真实交易结果、最终利润和现金回收已经发生 | `unknown` |

## 当前决策

1. 当前文档统一使用“经营事实核验案卷”解释现有 `experiment` 模块。
2. “经营实验闭环”“业务闭环”“订单跑完即闭环”等表述标记为 `superseded`。
3. 保留事实真实性、Owner 审批、对象一致性、结算和现金对账等安全约束；这些约束有独立价值，但不再被包装为闭环。
4. 不因本次文档纠偏自动删除、重命名或重构代码。
5. 在完成新的领域设计前，停止围绕“经营实验闭环”扩建功能、验收标准和 Agent 能力。

## 后续若要建立真实反馈循环

必须先从一个具体经营问题开始，明确目标、可改变变量、外部执行方式、观测数据、归因限制、反馈规则和下一次执行。只有第二次动作确实由第一次结果触发并重新进入市场观测，才可以验证是否形成一轮反馈；一次结果不能证明可重复性或规模化。
