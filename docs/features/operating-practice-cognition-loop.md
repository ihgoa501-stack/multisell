# 凌镜经营实践—认识循环底座（架构草案）

> 状态：`draft / 待 Owner 确认`
> 日期：2026-07-13
> 对应方向：ADR-001 的经营事实系统、经营决策与反馈、小Q统一经营入口
> 当前边界：只供 Owner 本人使用；本文件不是开发授权，也不改变 Owner-only 方向

## 一句话说明

让凌镜能够把一次真实经营完整地记下来，从实践中形成认识，再让经过 Owner 确认的新认识进入下一次实践，并继续接受现实结果检验。

## 为什么建设

现在凌镜已经能保存许多事实，也有经营决定、受控行动和结果记录的工程骨架，但还不能可靠回答：

1. 当时面对的经营问题是什么？
2. 当时依据了哪些事实，又有哪些未知？
3. 小Q提出了什么构思，Owner为什么选择或拒绝？
4. 外部世界实际发生了什么行动？
5. 到约定时间后，真实结果怎样？
6. 原认识被支持、反对、发生冲突，还是仍然无法判断？
7. 新认识是否真正进入了下一次实践？

如果这些问题不能串起来，系统只能保存数据和执行功能，不能从经营实践中持续修正认识。

## 核心原则

### 1. 实践与认识分开

- **实践**：已经在现实或外部平台实际发生的行动，例如采购提交、价格调整、发布、履约或售后处理。
- **认识**：根据当时事实形成的解释、构思、判断和预期。认识可以被现实支持或推翻，不能冒充事实。
- **Owner 决定**：Owner 对具体构思作出的选择，不等于构思已经正确。
- **结果**：实践之后由权威来源观察到的事实，不允许为了符合预期而改写。

### 2. 每一轮都必须可追溯

一轮循环必须绑定同一个 Owner、同一个经营问题和明确的经营对象。使用的事实、构思、决定、行动、结果和下一轮都要能够互相追溯。

### 3. 失败和未知也是认识

结果只允许记录为：

- `support`：结果支持原构思，但不自动证明因果；
- `counter`：结果反对原构思；
- `conflict`：不同事实互相冲突；
- `unknown`：时间、证据或条件不足，无法判断。

系统不得把“行动后发生变化”自动写成“行动导致变化”。

### 4. 新认识不能自动执行

小Q可以形成下一次构思，但必须再次经过 Owner 决定、授权和必要审批，才能成为新的实践。

### 5. 不复制权威事实

订单、库存、采购、履约、结算、利润和现金继续由各自现有领域保存。循环底座只保存不可变引用、当时版本和校验摘要，不建设第二套数据中心。

## 总体架构

```text
经营事实系统
  提供真实对象、来源、时间和可信等级
        ↓
经营认识案卷
  保存问题、目标、未知、构思、预期和观察期限
        ↓
Owner 决定
  选择、拒绝、暂停或要求更多证据
        ↓
受控实践
  只执行 Owner 冻结批准的具体行动
        ↓
结果观察
  在约定时间读取同一经营对象的权威结果
        ↓
认识更新
  support / counter / conflict / unknown
        ↓
下一轮构思
  引用上一轮认识，但重新经过 Owner 决定
```

## 一轮循环必须包含什么

### 一、经营问题

- Owner当前要解决的具体问题；
- 对应的商品、SKU、订单、采购或其他经营对象；
- 本轮目标、硬约束和停止条件；
- 本轮开始时间。

### 二、事实与未知

- 使用了哪些权威事实；
- 每条事实的来源、观察时间和可信等级；
- 当时明确不知道什么；
- 哪些外部变化可能影响结果。

### 三、构思

构思是一个待验证的经营设想，至少说明：

- 建议改变什么；
- 为什么这样建议；
- 预期看到什么结果；
- 什么时候开始观察、什么时候结束；
- 什么结果算支持、反对或无法判断；
- 风险和停止线。

构思固定为 `inferred`，不能直接写成事实。

### 四、Owner 决定

- `selected`：选择该构思进入授权流程；
- `rejected`：明确拒绝；
- `paused`：暂不执行；
- `request_more_evidence`：先补证据。

决定必须冻结具体对象、动作和输入。对象或输入变化后，旧决定失效。

### 五、真实实践

- 实际执行时间；
- 实际执行的对象和参数；
- 外部平台或现实回执；
- 执行成功、失败或结果待对账；
- 没有可靠回执时不得冒充成功。

### 六、结果与复盘

- 只读取同一经营对象的权威结果；
- 结果必须发生在实践之后，并处于约定观察期限内；
- 预期值和实际值由系统按确定规则计算，不允许调用方随意填写；
- 同时记录外部变化、同期其他行动和证据不足；
- 输出 `support / counter / conflict / unknown`，不自动输出因果结论。

### 七、下一轮

- 小Q根据本轮事实和复盘提出新的 `inferred` 构思；
- 下一轮明确引用上一轮；
- Owner接受后创建新的案卷；
- 上一轮记录保持不变，不能用后来的认识改写当时历史。

只有下一轮构思再次经过决定并进入真实实践，才算循环继续，而不是停留在总结文字。

## 小Q在循环中的职责

小Q可以：

- 整理当前问题涉及的权威事实；
- 明确已知、反证、冲突和未知；
- 提出带预期、期限和停止线的构思；
- 在观察期结束后解释预期与结果的差异；
- 检索相似历史循环，说明相同与不同条件；
- 提出下一轮构思。

小Q不能：

- 把自己的输出写成 `actual`；
- 代替 Owner 作出决定；
- 因为过去一次成功就自动执行；
- 修改历史事实、Owner决定或外部回执；
- 把相关性写成因果；
- 在没有足够证据时假装已经学会规律。

`xiao_q_support`：当前为 `deferred`。只有完整读取、解释、失败处理、证据追踪、权限和回归测试齐全后，才能标记 `active`。

## 与现有系统的关系

### 直接复用

- `platformtruth`：事实等级、对象身份、来源和系统职责；
- `businessdecision`：事实快照、AI建议和Owner不可变决定；
- `businessfeedback`：受控行动、结果观察和下一动作记录；
- 订单、库存、采购、履约、售后、结算、利润与现金的权威事实；
- 审批、权限、审计、幂等和失败待对账能力；
- 小Q现有的只读事实与建议边界。

### 必须补齐

- 明确的经营问题、目标、约束、未知和停止条件；
- 决策事实、行动目标和结果属于同一经营对象的强制校验；
- 实践前冻结的观察期限和评价方法；
- 由权威事实自动计算实际结果与偏差；
- 外部执行成功的可靠凭证；
- 复盘与下一轮案卷的不可变关联；
- 小Q检索历史循环时的可信度和适用范围说明。

### 不建设

- 第二套数据库、数据仓库或万能数据中心；
- 把所有领域合并成一个巨大对象；
- 当前阶段的模型在线训练或自动强化学习；
- 多用户、租户、跨用户经验池或群体规律；
- 绕过Owner的自动实践。

## 第一条纵向验证

第一条循环不应同时覆盖所有经营活动。实施规划时只选择一种已经具备真实事实来源和可靠执行回执的经营动作，例如单一SKU的一次采购、价格或发布动作。

必须完整跑通：

```text
真实经营问题
→ 冻结当时事实和未知
→ 小Q提出构思
→ Owner决定
→ 真实行动与外部回执
→ 等待观察期限结束
→ 自动读取权威结果
→ 形成复盘
→ 小Q提出下一轮构思
→ Owner决定是否再次实践
```

具体选择采购、价格还是发布，必须先确认哪个入口真正具有外部执行凭证；不能为了演示而使用假成功。

## 验收标准

### 工程通过

- 重启后仍能恢复完整历史；
- 前后对象不一致时失败关闭；
- 行动前数据不能冒充行动后结果；
- 观察期限未结束时保持 `unknown`；
- 实际结果不能手填覆盖权威事实；
- 无外部回执不能标记实践成功；
- 下一轮不能绕过Owner决定；
- 自动测试、PostgreSQL约束测试和Owner页面验收通过。

### 真实使用通过

- Owner能够看懂一轮完整经历；
- 小Q下一次建议能够准确引用上一轮事实和复盘；
- Owner能够指出系统认识错误并保留纠正记录；
- 至少完成两轮真实“实践—认识”循环。

### 不能宣称

- 一轮成功不能证明规律成立；
- 工程测试通过不能证明经营有效；
- 保存了复盘不能证明模型已经学习；
- 多轮相关结果不能自动证明因果。

## 当前证据状态

- `policy`：Owner明确要求凌镜具备经营实践—认识循环能力。
- `implemented / automated_verified`：现有代码已有事实快照、AI建议、Owner决定、受控行动、观察和下一建议的部分骨架。
- `planned`：本草案所述统一循环合同、可靠结果计算、观察期限和下一轮关联尚未实现。
- `unknown`：第一条真实循环选择、真实外部回执可用性、长期学习价值和未来是否需要模型训练。
