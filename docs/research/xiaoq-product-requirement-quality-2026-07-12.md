# 小Q产品需求质量审计

> 日期：2026-07-12
> 范围：评估 Owner 原始要求的产品需求质量，不评价 Owner 人格或是否适合创业
> 原始要求：“做一个与本项目相关、能调用整个系统、以后新增功能也同步扩展、名叫小Q的 Agent；AI 自行拆解、调研、开发，并派多个 Agent。”
> 结论等级：项目现状为 `actual`；产品判断与建议为 `inferred`；外部方法论为 `quoted`

## 1. 结论

这项要求作为**产品愿景和方向输入是合理的**，作为直接交给开发执行的**完整产品需求还不合格**。

专业产品经理完全可能先用类似的一句话提出方向，但不会停在这里。随后通常会把它转换为：明确用户问题、使用场景、首个端到端流程、权限边界、成功指标、非目标、风险、验收与停止条件。否则“能调用整个系统”和“后续都要同步开发”会变成无法证明完成的永久工程任务。

最准确的判断是：

- “小Q是 Owner 使用凌镜的统一入口”是好的产品方向；
- “调用整个系统”是过宽的解决方案描述，必须改成逐项登记和验收的能力目录；
- “新增功能同步增加小Q”是合理的演进原则，但不应强制所有功能都接入，应允许 `active / deferred / not_applicable`；
- “AI自行拆解、调研、开发”是合理的协作授权，但必须受范围、证据、测试和高风险审批约束；
- “派多个 Agent”不是产品价值，也不是必选架构，只是某些可独立任务的执行手段。

因此推荐：**保留小Q长期方向，不批准一次性“全系统接入”；用一个真实 Owner 问题建立第一条可测闭环，验证有用后按能力逐项扩展。**

## 2. 判断依据

### 2.1 产品管理的一手资料

- `quoted`：Atlassian 的 PRD 指南要求说明产品目的、用户需要、关键功能和成功标准；其推荐内容还包括目标、背景、假设、用户故事和明确的范围外事项。来源：[Atlassian — How to create a product requirements document](https://www.atlassian.com/agile/product-management/requirements)。
- `quoted`：Atlassian 的 PRD 模板要求写明目标及其衡量指标，而不是因为想做某个功能就建设它。来源：[Atlassian — Product requirements document template](https://www.atlassian.com/software/confluence/templates/product-requirements)。
- `quoted`：SVPG 区分“给团队问题和结果”与“给团队功能清单”；受赋能的产品团队应对结果负责，并在发现阶段验证价值、可用性、可行性和业务可持续性风险。来源：[SVPG — Discovery vs. Design](https://www.svpg.com/discovery-vs-design/)、[SVPG — Product vs Feature Teams](https://www.svpg.com/product-vs-feature-teams/)。
- `quoted`：SVPG 强调交付功能不是最终结果；如果没有产生所需影响，团队需要继续迭代方案。来源：[SVPG — Changing How You Solve Problems](https://www.svpg.com/changing-how-you-solve-problems/)。

### 2.2 Agent建设的一手资料

- `quoted`：OpenAI 将 Agent 描述为能代表用户完成工作流、通过工具读取或采取动作，并在明确护栏内动态选择工具的系统；其核心组成是模型、工具和指令。来源：[OpenAI — A practical guide to building agents](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)。
- `quoted`：OpenAI 建议工具采用标准化、可复用、测试充分的定义；高风险或不可逆动作应有人介入，并应设置失败或重试阈值。来源同上。
- `quoted`：Anthropic 建议从最简单可行方案开始，只在确有需要时增加复杂度；预定义工作流更可预测，Agent适合确需模型动态决策的场景。来源：[Anthropic — Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)。
- `quoted`：Anthropic 认为并行化适合可真正拆分的子任务，或需要多个独立视角来增加置信信息的场景，不是所有任务的默认做法。来源同上。

### 2.3 对原要求的推断

- `inferred`：原要求表达的是一个有价值的产品方向，但还没有证明“小Q统一入口”比当前页面与人工操作更省时、更准确或更安全。
- `inferred`：若按字面一次性接入整个系统，会优先增加集成面、权限面和维护负担，而不是优先证明 Owner 获得了经营价值。
- `inferred`：让 AI 自行拆解是适合单人 Owner 的工作方式；但“谁执行”不能替代“为什么做、做到什么算成功”。

## 3. 项目当前事实

### 已直接核验的 `actual`

1. 当前方向是只供 Owner 本人使用的跨境商品实验与经营内部系统，不服务外部软件客户。
2. 当前唯一经营主线是候选市场比较，经过真实实验、订单、售后、结算，走到最终净利润和现金对账。
3. 小Q已有稳定 ID `xiao_q`、后端 `/api/v1/xiao-q` 和前端 `/xiaoq`。
4. 小Q当前只登记两个 active 能力：
   - `demand_case.read`；
   - `demand_case.decision_card.read`。
5. 当前小Q只能解释一个指定需求案件和决策卡；它不是任意问题的全系统 Agent。
6. 当前实现包含 Owner 数据隔离、模型调用、trace、证据引用、stub 显式标记和失败不伪装成功的测试。
7. 订单、实验、1688草稿、售后、结算、现金、平台动作等尚未成为小Q active Capability。
8. 项目中仍存在 stub、mock、薄平台适配器和未连接真实经营事实，不能把“代码存在”写成“小Q已经能可靠调用”。

### 当前仍为 `unknown`

- Owner 是否会重复使用小Q完成同一种经营任务；
- 小Q相对直接使用页面能节省多少时间；
- 小Q回答的事实准确率、引用完整率和错误恢复表现；
- 维护每项 Capability 的长期成本；
- 真实模型、真实数据源和生产凭据下的可靠性；
- 小Q是否会改善最终经营结果。

## 4. 原要求逐项评分

评分标准：1分为几乎无法指导决策，5分为可以直接指导边界清晰的产品发现或开发。

| 原要求组成 | 分数 | 合理之处 | 缺失或风险 |
|---|---:|---|---|
| “与本项目相关” | 3/5 | 限定了产品上下文 | 没说明具体服务哪条经营主线、解决 Owner 哪个高频问题 |
| “Agent叫小Q” | 4/5 | 稳定名称有利于建立统一心智和身份 | 名称不是价值或验收标准 |
| “能调用整个系统” | 2/5 | 统一入口方向清楚 | “整个系统”无边界；读、建议、写入、资金动作风险完全不同；无法一次验收 |
| “新增功能也继续增加小Q开发” | 3/5 | 抓住了长期一致性和避免能力脱节 | 强制全部同步会阻塞业务功能；有些功能不适合对话调用；需要 deferred/not_applicable |
| “AI自行拆解、调研、开发” | 3/5 | 对单人 Owner 是高效率授权方式 | 缺少决策边界、预算、时间、证据和验收；AI可能把拆解本身当进展 |
| “派多个Agent” | 2/5 | 独立研究、反证、代码审查可受益于并行 | 把实施方式预设成需求；会增加成本、重复、冲突，且多个Agent一致不提高事实等级 |
| 用户与问题定义 | 3/5 | 用户可推断为 Owner | 具体任务、发生频率、现有替代方式和最大痛点没有写出 |
| 首个闭环与优先级 | 2/5 | 已有候选市场上下文可承接 | 原话没有限定第一个问题和完成边界 |
| 成功指标与验收 | 1/5 | 无 | 无法判断有用、失败或何时停止 |
| 安全、权限和非目标 | 1/5 | 无 | “调用整个系统”可能被误解为超级权限或自动写入 |

**总评：24/50。** 这是一个合格的“产品想法/Owner方向输入”，不是一个可以直接声称完成的 PRD。低分不代表想法错误，而是缺少产品经理应补齐的转换工作。

## 5. 专业产品经理会不会这样提

### 会这样开始

产品经理在早期讨论中可能会说：

> 我希望有一个叫小Q的经营助手，成为 Owner 使用整个凌镜的统一入口，未来系统增加能力时它也能持续扩展。

这种表达适合对齐愿景、命名和总体方向。

### 不会只这样结束

一个对结果负责的产品经理会继续追问并写清：

1. Owner现在为了完成哪项任务，要在多少页面之间切换或手工整理什么？
2. 哪个任务最频繁、最痛、最值得先验证？
3. 小Q第一版只需要读什么、解释什么、绝不能做什么？
4. 用页面直接操作的当前基线是多少？
5. 什么数据证明小Q比现状更好？
6. 错误事实、越权、隐性失败和模型费用如何发现？
7. 哪些动作必须由 Owner批准？
8. 什么时候停止扩展或退回普通工作流？

所以专业差别不在于“第一句话是否像这样”，而在于是否把第一句话继续转化为**问题、结果、边界和证据**。

## 6. 产品经理版 One-pager

### 名称

小Q：凌镜 Owner 经营助手

### 状态

`discovery / limited implementation`。已有需求案件只读解释能力；全系统调用尚未实现。

### 用户

唯一用户是凌镜 Owner本人。

### 用户问题

Owner在经营决策中需要跨越多个模块查找案件、证据、反证、实验、订单、售后与利润状态。当前需要理解不同页面和对象关系，且容易把 mock、推断、代码状态与真实经营事实混淆。

### 目标结果

Owner能用自然语言询问一个明确的经营案件，小Q在权限和证据边界内读取已登记能力，给出可追溯的状态解释、关键反证、未知项和下一步；Owner减少手工查找和整理，但保留所有高风险决定权。

### 首个端到端流程

```text
Owner选择一个真实候选市场案件并提问
→ 小Q调用案件与决策卡只读能力
→ 返回当前裁决、最强支持、最强反证、关键未知和来源链接
→ Owner能追问依据并进入原始案件/trace
→ Owner决定继续取证、淘汰或保持待定
```

第一版不扩大到订单、发布、采购或资金动作。它只验证“小Q是否比直接浏览需求案件更有用”。

### 核心产品原则

1. 小Q是唯一面向 Owner 的 Agent身份，但不是数据库超级用户。
2. 所有系统调用必须通过版本化 Capability；不直接访问任意表，不复制领域规则。
3. 领域状态机裁决事实，模型只解释和建议。
4. 证据、反证、未知、来源、观察时间与trace不能被隐藏。
5. 每项能力单独声明 read / suggest / mutate、权限、审批、副作用、失败和恢复。
6. 新功能必须评估小Q支持状态，但不强制立即 active。

### 用户故事

> 作为唯一 Owner，当我评估一个候选市场时，我希望直接询问小Q“现在能否进入实验，为什么”，从而在不逐页拼接信息的情况下看到系统裁决、支持证据、反证、未知和可追溯来源，并由我决定下一步。

### 功能范围（第一版）

- 小Q固定身份和统一入口；
- 读取当前 Owner的指定需求案件和决策卡；
- 以结构化方式展示结论、支持、反证、未知、来源和trace；
- 明确标注 mock / inferred / unknown；
- Provider失败时返回失败，不生成伪成功建议；
- Owner隔离、RBAC和审计；
- 记录一次任务的时间、Token和模型成本。

### 验收标准

1. 对一个有真实来源的候选案件，回答中的关键事实100%能跳转或追溯到系统对象或来源；无来源内容必须标为推断或未知。
2. 小Q不得改变领域 verdict，不得把 mock / inferred / unknown 升级为 actual。
3. 无权限、跨 Owner、Provider失败、trace写入失败时均不得返回成功。
4. 至少完成5次同类真实任务试用，并与直接使用页面的人工基线比较。
5. Owner能在回答后正确说出“当前结论、最强反证、尚缺什么、下一步由谁决定”。

### 发布决策

- 若通过指标且 Owner愿意重复使用，再接下一个最相关的只读能力；
- 若只减少点击但增加复核负担，修正信息结构，不扩大能力；
- 若无法稳定保持事实边界，暂停 LLM解释，保留确定性决策卡。

## 7. 必须补充并冻结的成功指标

首次正式试用前先测人工基线，再冻结阈值。建议使用以下指标：

### 主指标

- **任务完成时间**：同一类候选市场判断，从开始到 Owner能作出下一步决定的中位耗时；目标可暂定比人工页面流程下降30%，但该阈值属于 `estimated`，基线后确认。
- **可追溯事实完整率**：回答中的关键事实有系统对象、来源或快照支持的比例；目标100%。
- **事实升级错误数**：把 mock / inferred / unknown写成 actual，或声称不存在的成交、利润、批准；目标0。

### 护栏指标

- 跨 Owner数据泄露：0；
- 未审批高风险动作：0；
- Provider或trace失败被显示为成功：0；
- 无来源关键结论：0；
- 单任务Token、费用、工具次数和耗时：必须记录；限额在真实基线后冻结；
- Owner复核时间：不能比现有页面流程显著增加。

### 使用信号

- 在5次同类任务中，Owner主动选择小Q而非直接页面的次数；
- Owner是否根据回答完成了明确的下一步，而非只阅读聊天内容；
- 追问中有多少是因为信息缺失或表达不清，而不是业务本身仍未知。

这些指标只能证明“小Q在该任务上是否有用和可靠”，不能证明整个凌镜成功，也不能证明小Q提高了最终利润。

## 8. 必须明确的非目标

第一阶段不做：

- 一次性接入整个系统；
- 直接数据库自由查询或自由写入；
- 自动采购、发布、投放广告、退款、转账或修改预算；
- 把A1—A12、G0—G3全部包装进小Q；
- 为了“像Agent”而加入更多Agent、长期自治、记忆或复杂编排；
- 新增国家、平台、类目或商品方向；
- 外部 SaaS、多租户、订阅、公共API或外部用户；
- 用回答数量、Capability数量、Token消耗或代码量衡量成功；
- 把小Q建议当作市场、成交、利润或现金已经发生的证据。

## 9. 停止条件

出现任一情况，停止扩展新 Capability，先修复或回退：

1. 任一次跨 Owner数据泄露、未审批外部写入或高风险越权；
2. 任一次把 mock / inferred / unknown升级为 actual并影响 Owner决定；
3. 连续两次真实任务出现来源错配、错误对象关联或trace不完整；
4. 完成5次同类试用后，任务完成时间或复核负担没有改善；
5. Owner并不重复使用，仍优先直接打开页面；
6. 新能力维护成本持续高于它减少的手工工作；
7. 开发转向“覆盖更多模块/Agent”而没有对应的真实 Owner任务；
8. 当前经营主线的关键闭环因小Q建设被推迟。

回退方案：保留确定性领域页面与决策卡，关闭对应小Q能力；不因已经投入开发而继续扩张。

## 10. “以后新增功能也要增加小Q”的正确规则

不应规定“每个新功能必须立即让小Q调用”，应规定“每个新功能必须完成小Q适配判断”。设计评审必须填写：

```text
xiao_q_support: active | deferred | not_applicable
owner_problem:
capability_id:
mode: read | suggest | mutate
evidence_source:
required_permission:
approval_required:
external_side_effects:
failure_and_recovery:
audit_and_trace:
acceptance_test:
deferred_or_not_applicable_reason:
```

- `active`：真实 Owner任务需要，契约、权限、证据、失败处理和测试齐全；
- `deferred`：未来可能需要，但当前没有使用证据或前置事实链未完成；
- `not_applicable`：内部技术设施或不适合对话调用，小Q无需暴露。

这既保持小Q长期一致性，也避免所有业务功能被对话层绑架。

## 11. “派多个Agent”的正确使用规则

多个Agent是实施策略，不写入产品成功标准。只有同时满足以下条件才使用：

- 子任务可独立完成，输入和输出边界清楚；
- 并行能实质降低时间，或确实需要独立反证/审查；
- 结果能由测试、来源或确定性规则验证；
- 合并责任明确，不把多个Agent一致当作事实证明；
- Token、费用和重复劳动可记录。

适合：独立外部研究、反证研究、代码审查、测试覆盖审计。
不适合：需要连续理解同一业务状态的小改动、无法独立验收的架构发散、单纯为了“更智能”而增加角色。

## 12. 最终裁决

| 问题 | 裁决 |
|---|---|
| 这个方向合理吗？ | 合理，适合作为长期产品方向 |
| 原话能直接当完整需求吗？ | 不能，缺用户任务、首个闭环、指标、边界与停止条件 |
| 产品经理会这样说吗？ | 会这样开始，但专业产品经理必须继续完成需求转换和发现 |
| 应该现在接入整个系统吗？ | 不应该；按真实任务逐项登记 Capability |
| 新功能要考虑小Q吗？ | 要做适配判断，不等于必须同步 active |
| AI能自行拆解开发吗？ | 可以在已冻结的结果、边界和验收内自主执行 |
| 必须派多个Agent吗？ | 不必须；只在可独立、可验证且并行有价值时使用 |

推荐下一步不是继续写“大而全”规划，而是用当前已经实现的两个只读 Capability 完成5次真实候选市场问答，记录人工基线、准确性、复核时间和是否真正影响下一步。得到这些事实后，再决定第二个业务域接实验、1688草稿还是订单结果。
