# 凌镜真实可运行系统完善计划

> 日期：2026-07-13
> 状态：`current plan`
> 目的地：[ADR-001](../decisions/ADR-001-owner-complete-commerce-platform.md)
> 运行方法：[ADR-002](../decisions/ADR-002-practice-cognition-operating-method.md)
> 生产操作唯一入口：[OWNER_AND_AI_DEPLOYMENT_RUNBOOK](../ops/OWNER_AND_AI_DEPLOYMENT_RUNBOOK.md)

## 目标

把凌镜从“代码、自动测试和本地隔离验收已有大量证据，但真实经营仍有大量 unknown”，推进到：

> Owner 能在正式受控环境中完成从市场与机会、商品与货源、渠道准备，到订单、履约、售后、结算、银行到账、最终利润和下一次经营决定的真实流程；外部写入安全、失败可恢复、结果可追溯。

本计划完善的是 ADR-001 的完整 Owner 自用平台，不把第一条可运行流程当成产品上限。

## 当前基线

以带日期审计为准：

- `implemented / automated_verified / manually_verified`：当前代码已有大量领域能力、自动测试、迁移验证和本地隔离运行验收；
- `actual`：最新跨层本地验收使用明确标记的 mock 经营事实，没有执行真实渠道或供应商写入；
- `unknown`：正式服务器、真实市场选择、真实渠道权限、真实1688商品、真实发布、订单、履约、售后、结算、银行到账和最终利润尚未形成一条完整外部证据链。

最新事实读取顺序：

1. `docs/research/project-truth-audit-2026-07-13.md`；
2. `docs/research/project-truth-audit-2026-07-12.md`；
3. `docs/research/project-truth-audit-2026-07-11.md`。

## 总验收路径

```text
平台真相和正式环境
→ 真实市场与渠道资格
→ 真实商品、货源与渠道准备
→ 受控采购、发布和交易
→ 履约、售后与异常
→ 结算、银行到账与最终利润
→ 小Q解释、Owner决定与下一次行动
→ 重复运行与恢复演练
```

## P0-1：固定真实可运行基线

### 完成内容

- 以 `platformtruth` 领域合同和当前路由目录建立完整经营路径清单；
- 每个必要入口标记 `policy / planned / implemented / automated_verified / manually_verified / external_observed / reconciled / mock / unknown`；
- 标出 mock、stub、空成功、旧旁路和没有外部回执的入口；
- 记录当前正式环境、账号、凭据、外部权限和真实数据的可用情况，但不输出秘密值；
- 将每个缺口映射到 ADR-001 的一个纵向单元。

### 通过条件

- 所有必需经营步骤都有唯一权威入口、当前证据等级和下一验收动作；
- 不再依据模块数量、页面或测试数推断可用性；
- 未知项有负责人（Owner或AI）、所需外部条件和停止条件。

## P0-2：完成正式运行底座

### 完成内容

- 严格使用唯一部署手册完成正式环境初始化、配置和迁移；
- 验证HTTPS、身份、Owner权限、审批、审计、幂等、限流和秘密管理；
- 验证监控、告警投递、备份、恢复、数据库迁移、回退和故障处理；
- 验证付费Provider和外部写入的预算、停止、结果未知与对账机制；
- 清除正式Owner入口中的mock展示、stub回退和假成功。

### 通过条件

- 正式环境部署和重启后可恢复；
- 备份能够实际恢复，而不只是存在脚本；
- 审批或审计失败时外部写不发生；
- 外部结果未知时停止重试并进入对账；
- Owner能按手册理解、停止和恢复系统。

## P0-3：真实市场、渠道和经营资格

### 完成内容

- 在 `/demand-cases` 使用带来源和观察时间的真实研究，而不是静态基线或mock；
- Owner形成最新、不可变的市场决定；
- 验证目标国家、消费者、渠道、收款、履约、合规和售后条件；
- 验证真实渠道账号、读取权限、写入权限、sandbox/production差异和限制；
- 所有未知权限在进入采购或发布前失败关闭。

### 通过条件

- 形成一个真实Owner决定的市场与商品机会；
- 真实渠道资格和限制有外部来源与时间证据；
- 未验证的国家、渠道和商品不会自动进入后续流程。

## P0-4：真实商品、货源与渠道准备

### 完成内容

- 使用Owner浏览器完成真实1688页面采集、重复观察、断网恢复和字段人工验收；
- 核验供应商主体、报价、MOQ、SKU、样品、交期、库存和变化；
- 完成精确成本、汇率、物流、关税、平台费、素材权利和合规证据；
- 图片与内容只进入内部草稿，真实发布继续独立审批；
- 建立canonical SKU、供应商SKU和渠道SKU的稳定映射；
- 对真实草稿完成Owner审阅、修改、批准和防篡改验收。

### 通过条件

- 至少一个真实商品机会完成货源与草稿准备；
- 关键字段不再依赖mock或未经核验的quoted声明；
- 成本可复算，图片权利和合规通过当前门禁；
- 草稿未获独立发布批准时不会进入渠道。

## P0-5：真实采购、发布和交易经营

### 完成内容

- 采购请求绑定同一Owner的供应商、SKU、成本版本、库存和Owner决定；
- 外部采购提交、供应商接单、失败、部分/全部收货使用不可变回执推进；
- 发布只执行Owner批准的exact草稿、渠道、账号和输入哈希；
- 渠道返回结果不明确时进入对账，不自动重试；
- 真实订单摄取、SKU映射、库存预占/扣减/释放形成不可变账本；
- 价格、广告和库存外部调整继续保持Owner授权与风险上限。

### 通过条件

- 至少一个真实采购或发布动作有可核验外部回执；
- 至少一条真实订单路径能回到同一Owner、账号和SKU；
- 任何对象、审批、输入或Owner不一致都失败关闭；
- 无真实副作用的命令不能标记为成功。

## P0-6：真实履约、售后和异常闭合

### 完成内容

- 包裹、承运商事件和签收绑定同一订单；
- 只有可信外部事件能升级为实际履约事实；
- 售后请求、Owner决定、外部退款/争议执行和终局回执分层保存；
- 退款、拒付、退货、丢件、库存差异和执行结果未知进入Owner异常队列；
- 失败恢复、人工对账和重复回执幂等通过验收。

### 通过条件

- 一笔真实订单完成履约或明确终止；
- 售后观察期结束且不存在未决事项，或未决事项被明确阻断；
- Owner能够从异常入口恢复或结案，而不是直接改数据库状态。

## P0-7：真实结算、现金和最终利润

### 完成内容

- 摄取真实平台结算及明细，绑定同一Owner、账号、订单和币种；
- 汇总真实商品成本、采购、履约、平台费、广告、税费和售后终局；
- 银行或支付到账与结算应收分开保存；
- 只有同对象、同币种、完整金额匹配时升级为 `reconciled`；
- 最终利润保留计算版本、来源清单和无法归属的金额；
- 负利润、未回款或未决售后不得被“学习”改写成成功。

### 通过条件

- 至少一笔真实订单完成结算到银行到账的可复算对账；
- 最终利润来自权威明细，不接受调用方手填覆盖；
- Owner能够理解收入、成本、现金和最终利润之间的差异。

## P0-8：经营结果进入下一次行动

### 完成内容

- 经营问题、目标、事实、未知、AI建议、Owner决定和行动分层保存；
- 行动必须有真实执行时间和外部回执；
- 结果必须来自同一经营对象，并发生在冻结观察期限内；
- 系统按权威字段计算实际结果和偏差；
- 小Q只形成 `inferred` 下一建议，Owner决定是否进入下一次行动；
- 下一案卷引用上一轮，但不改写历史。

### 通过条件

- 至少完成两轮真实“实践—认识—再实践—再认识”；
- 第二轮行动明确引用第一轮结果；
- 结果只记录 `support / counter / conflict / unknown`，不自动宣称因果；
- 小Q不能形成Owner决定或绕过审批执行。

## P0-9：平台级持续经营验收

### 完成内容

- 从Owner登录开始重复运行完整主路径；
- 演练服务重启、数据库恢复、Provider超时、渠道结果未知、重复回执和告警；
- 核对审计、成本、预算、异常和所有外部写入；
- 生成新的带日期项目真相审计；
- 将仍未完成的纵向单元继续列入平台完善队列，不因首条路径成功宣布完整平台完成。

### 通过条件

- Owner能够在没有开发者直接修改数据库的情况下完成、停止和恢复经营任务；
- 一次完整运行和一次故障恢复均有证据；
- 项目状态准确区分工程完成、外部观察、经济对账和重复经营；
- 后续工作继续映射到ADR-001，而不是扩张无关能力。

## 执行规则

每次只推进当前最早未通过的门槛：

1. 先核对已有能力，禁止重复建设；
2. 修复阻塞真实运行的最小根因；
3. 完成正常路径、失败路径、安全、测试和文档；
4. 运行对应环境验收；
5. 记录实际证据等级、未知和下一门槛；
6. 未通过时继续修复，不以新功能绕开；
7. 通过后进入下一门槛，平台目的地不缩小。

## 停止和升级条件

- 需要真实资金、采购、发布、退款或不可逆外部写时，必须由Owner形成具体决定并批准exact输入；
- 缺少账号、凭据、市场选择或现实事件时，标记阻塞条件，不用mock冒充完成；
- 发现目标市场、渠道或商品不成立时，停止该经营路径并回到市场与机会层，不用继续开发改写经营失败；
- 出现数据损坏、资金风险、权限绕过、无法对账或恢复失败时，停止外部写，优先恢复与审计；
- 只有真实重复证据证明现有记录/检索不足时，才评估模型训练或在线学习。
