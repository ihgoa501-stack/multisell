# 凌镜 LingMirror 项目收口与 Agent 协作规范

说明：`MultiSell` 是历史技术项目名；当前产品品牌为 `凌镜 LingMirror`。

更新时间：2026-06-15

## 这份文档解决什么问题

当前项目的真实情况是：

非技术负责人提出业务目标，Codex 负责规划和验收，其他 Agent 负责编码实现。

这种模式可以继续用，但必须有明确边界。否则会出现：

- 文档很多，但系统不可用。
- 功能很多，但链路不闭环。
- Agent 都说完成了，但页面还是旧的、容器没更新、测试没跑全。
- 非技术负责人被迫判断代码质量。
- Codex 被反复拉去救火，而不是控制项目节奏。

从现在开始，本项目采用下面的协作规则。

---

## 角色分工

### 负责人，也就是你

你只负责三件事：

1. 说明业务目标。
2. 判断页面和流程是不是你要的。
3. 决定优先级。

你不需要判断：

- 哪个文件该改。
- 数据库表怎么设计。
- 测试怎么写。
- Agent 写的代码是否可靠。
- Docker、迁移、构建、接口是不是对。

这些交给 Codex 验收。

### Codex

Codex 是技术负责人和验收人。

Codex 负责：

- 把业务目标翻译成技术计划。
- 拆分任务给其他 Agent。
- 限制任务范围，避免 Agent 发散。
- 审查其他 Agent 的实现。
- 运行测试和构建。
- 判断是否真的完成。
- 告诉你当前真实进度和风险。

Codex 不应该只做：

- 一直写新规划。
- 不验收就继续派新任务。
- 只听 Agent 口头说“完成”。

### 其他 Agent

其他 Agent 是执行者。

其他 Agent 只能做：

- 按指定规划实现。
- 修改规划允许的文件。
- 补必要测试。
- 运行指定验证命令。
- 汇报结果。

其他 Agent 不能做：

- 自己决定新功能。
- 顺手重构无关模块。
- 回滚别人改动。
- 跳过测试。
- 只说“已完成”但不提供验证结果。

## 项目当前阶段判断

MultiSell 已经不是空项目，也不是纯 Demo。

当前处于：

```text
核心业务闭环补齐阶段
```

现在最重要的不是继续加页面，而是把关键链路收口成一个可用版本。

优先级顺序：

1. 商品数据可靠。
2. 物流计算可靠。
3. 库存和订单闭环可靠。
4. 利润测算可靠。
5. 平台订单接入。
6. 报表和运营分析。
7. 真实物流商 API。

## 目前最大风险

### 风险 1：功能完成不等于系统可用

一个功能只有代码合并是不够的。

必须同时满足：

- 后端测试通过。
- 前端构建通过。
- 页面能看到。
- Docker 或运行环境已更新。
- 关键流程能手动跑通。

否则只能算“代码写了”，不能算“功能完成”。

### 风险 2：多个 Agent 容易互相覆盖

当前 git 工作区有大量未提交改动和新增文件。

规则：

- 任何 Agent 不得执行 `git reset --hard`。
- 任何 Agent 不得回滚自己没做的改动。
- 任何 Agent 改同一个文件前，必须先读当前文件。
- 改完必须说明改了哪些文件。

### 风险 3：页面不是最新版本

之前已经出现：

- 本地代码已构建。
- 但 `localhost:3000` 容器仍是旧前端。
- 导致你看到的页面和代码不一致。

以后每次前端功能完成后，验收必须确认：

```bash
cd frontend && npm run build
```

并确认运行中的前端服务已经使用最新构建。

### 风险 4：测试数据污染业务判断

测试产品很多时，不代表系统坏了。

需要区分：

- 数据真的没写入。
- 数据写入了但分页看不到。
- 数据写入了但被筛选条件隐藏。
- 页面使用旧构建。
- 前端读取接口结构错误。

## 什么叫“完成”

以后任何任务不能只说“已完成”。

必须按下面格式验收。

### 后端任务完成标准

必须满足：

```bash
cd backend && python3 -m pytest <相关测试> -q
```

如果涉及共享模块，还要跑：

```bash
cd backend && python3 -m pytest -q
```

并汇报：

```text
后端测试：196 passed, 22 warnings
```

测试失败时，不能继续做新功能。

### 前端任务完成标准

必须满足：

```bash
cd frontend && npm run build
```

并汇报：

```text
前端构建：通过
```

如果是页面功能，还必须手动打开页面确认。

### Docker / 页面任务完成标准

如果你是通过 `localhost:3000` 看页面，还必须确认运行环境已更新。

至少确认：

```bash
docker compose ps
```

如果只构建了本地 `frontend/dist`，但容器没更新，不能算页面完成。

### 最终统一检查

每个任务完成前必须跑：

```bash
git diff --check
```

## Agent 工作流程

### Step 1：Codex 写规划

规划必须包括：

- 目标。
- 当前问题。
- 文件范围。
- 数据结构或接口变化。
- 任务拆分。
- 测试要求。
- 验收命令。
- 手动检查步骤。
- 交给 Agent 的提示词。

规划保存到：

```text
docs/superpowers/plans/YYYY-MM-DD-xxx.md
```

### Step 2：你把规划交给执行 Agent

你不要自己解释技术细节。

直接复制规划里的 handoff prompt。

### Step 3：执行 Agent 写代码

执行 Agent 必须遵守：

- 只改规划范围内的文件。
- 先读相关文件。
- 不做无关重构。
- 不回滚他人改动。
- 必须补测试，除非规划明确不需要。

### Step 4：执行 Agent 汇报

执行 Agent 必须按这个格式汇报：

```text
任务名称：

改动文件：
- ...

完成内容：
- ...

验证命令：
- cd backend && python3 -m pytest ... -q：通过/失败
- cd frontend && npm run build：通过/失败
- git diff --check：通过/失败

手动检查：
- 已检查 / 未检查

遗留问题：
- 无 / ...
```

### Step 5：Codex 验收

Codex 不接受“口头完成”。

Codex 必须：

- 看 git diff。
- 看关键代码。
- 跑测试。
- 跑构建。
- 必要时打开浏览器验证。
- 给出真实结论。

结论只能是三种：

```text
通过
部分通过，需要补
不通过，必须返工
```

## 后续任务优先级

现在不要随便继续加功能。

建议后续按这个顺序推进。

### P0：项目收口

目标：确认当前已有功能真实可用。

任务：

1. 跑全量后端测试。
2. 跑前端构建。
3. 确认 Docker 页面是最新版本。
4. 手动跑通：
   - 登录。
   - 商品列表。
   - 新增商品。
   - 补齐物流数据。
   - 商品跳转运费计算器。
   - 手动运费计算。
   - 订单创建。
   - 库存锁定和扣减。

### P1：订单录入体验

当前没有真实平台订单接入前，需要先让人工订单录入顺畅。

目标：

- 可以从页面创建订单。
- 选择 SKU。
- 自动读取价格。
- 自动检查库存。
- 创建后锁库存。

### P2：运费报价结果保存

目标：

- 手动试算后可以保存一次报价结果。
- 后续订单可以选用历史报价。
- 方便比较不同供应商报价。

### P3：SKU 级物流字段整理

目标：

- SKU 列表显示 SKU 包装覆盖字段。
- SKU 可以一键带入运费计算器。
- 运费计算优先使用 SKU 包装，再回退商品包装。

### P4：平台订单接入

目标：

- 先支持 Excel 导入平台订单。
- 后续再接真实平台 API。

### P5：真实物流商 API

目标：

- 在报价规则稳定后，再接真实物流商 API。
- 不要过早接 API，否则调试成本高。

## 不允许的推进方式

下面这些做法以后都不要继续：

### 不要一次派多个 Agent 改同一块

例如：

- A 改商品列表。
- B 同时改商品导入。
- C 同时改运费计算器。

这些文件会互相影响。

### 不要只看 Agent 的“已完成”

必须看：

- 测试结果。
- 构建结果。
- 页面结果。

### 不要用“继续优化”当任务

任务必须具体。

错误说法：

```text
继续优化商品模块。
```

正确说法：

```text
商品列表新增按物流状态筛选，并补充后端查询测试。
```

### 不要直接接真实 API

真实物流 API、平台 API 都应该排在后面。

原因：

- 当前系统内部闭环还没完全稳定。
- 外部 API 会带来认证、限流、字段映射、错误码、费用等额外复杂度。
- 先把内部手动流程跑通，再接真实 API。

## 给你自己的判断标准

你不需要懂代码。

你只问这几个问题：

1. 这个功能我能不能在页面上操作？
2. 操作完数据有没有留下来？
3. 刷新页面后数据还在不在？
4. 出错时我能不能看懂原因？
5. 这个功能和下一个业务动作能不能连起来？

如果这些问题答不上来，就还没完成。

---

## 给 Codex 的固定验收指令

每次其他 Agent 说完成后，你可以直接发给 Codex：

```text
验收这个 Agent 的改动。不要继续写新功能。

请做：
1. 查看 git diff 和改动文件。
2. 判断是否符合规划。
3. 跑相关后端测试。
4. 跑前端 build。
5. 跑 git diff --check。
6. 如涉及页面，打开浏览器检查。
7. 告诉我：通过 / 部分通过 / 不通过，以及下一步该怎么办。
```

## 给执行 Agent 的固定开工指令

每次派任务时，你可以这样发：

```text
请严格按这个规划执行，不要扩展范围：
<粘贴规划文档路径>

规则：
1. 先读规划文档和相关文件。
2. 只修改规划允许的文件。
3. 不要回滚别人改动。
4. 不要做无关重构。
5. 完成后必须运行规划里的验证命令。
6. 最后按以下格式汇报：

任务名称：
改动文件：
完成内容：
验证命令与结果：
手动检查：
遗留问题：
```
