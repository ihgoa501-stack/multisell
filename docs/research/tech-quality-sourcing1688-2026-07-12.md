## 结论

**总分：27/35，开发质量“良好但未达到可放心长期扩展”。**

模块最强的部分是正确性与安全边界：受控采集先过市场/实验/Owner 闸门，不可变快照保存原始字节和哈希；草稿审批冻结内容；发布另设审批、幂等状态和超时后对账；多步写入普遍使用事务和行锁。最弱的部分是可维护性和验证层级：后端约 7,947 行、前端单页 1,043 行，核心文件过大；关键 PostgreSQL 触发器测试默认跳过；缺少覆盖 JWT→RBAC→审批中间件→领域服务→数据库的本模块真实 HTTP/E2E 验收。

当前没有发现可据此断言为 P0 的缺陷，但存在 3 个应在继续扩展前处理的 P1 基础问题。

## “开发得好 / 不好”的定义

开发得好不是“页面能开”或“测试很多”，而是：状态转换和数据约束正确；代码分工清楚；所有入口都经过 Owner、RBAC、审批和审计；常用查询有明确边界；正常、失败、并发和恢复路径均被自动验证；线上故障能定位且不会制造重复外部写。

开发得不好是：关键正确性只靠约定；一个改动需要理解超大文件；SQLite 测试代替 PostgreSQL 约束；测试绕开真实路由和中间件；外部调用失败后状态不明确；错误、耗时或重试无法追踪。分数含义：`5`=证据完整且无重要缺口，`4`=扎实但有局部债务，`3`=基本可用但有明显风险，`2`=脆弱，`1`=大部分缺失，`0`=不存在或已知错误。

## 主要发现

### P1：关键 PostgreSQL 不可变约束不属于默认强制测试

- `postgres_capture_integration_test.go:17-24` 明确只有设置 `SOURCING1688_POSTGRES_DSN` 才运行，否则 `t.Skip`。
- 本次 86 项通过包含该跳过，因此只能证明 SQLite/单元层与 race 检测通过，不能证明当前迁移后的 PostgreSQL 触发器、约束与代码仍一致。
- 风险：快照不可变、审批冻结等最重要保证可能在迁移漂移时不被普通 CI 发现。
- 好的完成标准：CI 建立一次性已迁移 PostgreSQL，强制执行不可变快照、唯一约束、审批冻结、发布并发 claim 和迁移上/下行验证；跳过应使该专用 job 失败。

### P1：核心实现和 Owner 页面过大，继续扩展的回归半径高

- `handler.go` 736 行承载约 20 个 HTTP 入口；`publish_service.go` 709 行同时负责请求冻结、批准、执行、持久化和对账；`acceptance_report.go` 667 行；前端 `page.tsx` 1,043 行。
- 这不是风格问题：审批、外部写、对账属于高风险路径，一个局部改动需要同时理解大量状态和 UI 状态。
- 好的完成标准：按受控采集、草稿、审批、发布/对账拆出小型 handler/component/use-case；状态枚举和转换仍保持一个事实源；拆分前后用现有测试锁定行为，不做功能扩张。

### P1：缺少本模块真实跨层验收门

- 后端测试主要直接构造 Service/Handler 和 SQLite；前端测试使用 mock API。仓库虽有 Playwright `sourcing.spec.ts`，未发现覆盖当前 `/sourcing1688` 受控采集→Owner 审核→草稿审批→发布审批保护的完整契约。
- 风险：路由注册、JWT 身份、RBAC、route catalog、审批一次性消费、响应结构和前端交互可分别通过测试，但组合后仍可能失败。
- 好的完成标准：至少建立两条非 mock 验收：无权限/无审批全链路失败关闭；授权 Owner 在隔离 PostgreSQL 中完成到 `approved_draft`，并确认未调用平台适配器。外部发布另用可记录调用的测试适配器验证一次性执行与超时对账。

### P2：旧 CRUD 语义仍与受控状态机共存

- `service.go:53-280` 仍保留无 Owner 参数的 `List/Get/Create/Update/Delete/Import/Reject/Summary`；`handler.go:86-185` 仍保留对应 Handler，但当前 `routes.go` 没有注册这些入口。
- 风险不是当前越权，而是未来误注册或内部复用时绕开受控工作流；测试仍维护这套接口，使“真正入口”不够清楚。
- 建议：确认无调用后废弃并删除，或明确移动到测试夹具/迁移兼容层；不得把它重新暴露为普通 CRUD。

### P2：错误边界与性能证据仍不完整

- `handler.go:59,80,90,95,109,118,135` 等旧/通用分支把 `err.Error()` 直接返回客户端；数据库或内部状态文本存在泄露风险。
- `BuildAcceptanceReport`、`ReadOwnerView` 以多次顺序查询拼装复杂视图，当前数据量小可接受，但没有基准、慢查询指标或查询数上限。
- 建议：统一外部安全错误码，详细错误只写带 request/correlation ID 的日志；为验收报告记录查询耗时并设慢查询告警，在真实数据量出现前不必提前做缓存。

## 推荐顺序与停止条件

1. 先把 PostgreSQL 约束测试变成 CI 强制门；若无法稳定运行，停止宣称数据库级保证已自动验证。
2. 加两条跨层验收，再拆超大文件；先有保护网，后降低复杂度。
3. 清理未注册旧 CRUD 语义并统一安全错误响应。
4. 在出现真实慢查询证据前，不建设缓存、队列或新的平台抽象。

达到“基础好”的最低条件：P1 全部关闭，聚焦 race 测试、强制 PostgreSQL 测试和跨层验收连续通过；外部发布仍保持独立 Owner 审批与可对账状态。
