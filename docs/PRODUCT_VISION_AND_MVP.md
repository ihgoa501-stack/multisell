# 凌镜 LingMirror 最终产品形态与第一可用版本定义

产品品牌：凌镜 LingMirror  
技术项目名：MultiSell

更新时间：2026-06-15

## 结论

凌镜 LingMirror 的最终定位不是普通商品后台，也不是单人使用的小工具。

最终定位：

```text
凌镜 LingMirror 是一个面向中小跨境电商团队的 AI Agent 协作运营平台。
```

它的长期目标是：

```text
人类经营者设定目标和审批关键决策，
多个 Agent 协作完成商品资料治理、物流测算、平台费用核算、利润决策、上架执行、订单履约和经营分析。
```

当前项目第一阶段的切入口：

```text
跨境电商商品上架前经营决策。
```

也就是先解决一个具体、可验证、业务价值明确的问题：

```text
一个商品在上架前，系统能否标准化判断它在哪个平台、哪个国家、什么售价、什么物流方案下值得上架。
```

---

## 为什么不能按当前个人画像来做

当前使用者是创业者本人，一个人同时承担老板、运营、仓库、财务等角色。

但这不是产品最终画像。

当前使用者的角色应该被定义为：

```text
第一个验证者，而不是最终产品画像。
```

如果完全按当前个人使用习惯设计，系统会变成个人效率工具，项目价值会变小。

MultiSell 应该服务的是未来的一类用户：

- 中小跨境电商卖家团队。
- 多平台运营团队。
- 商品运营和选品人员。
- 物流成本负责人。
- 需要用 Agent 提升运营效率的小型电商公司。

当前个人使用，只是为了验证业务流程是否成立。

## 最终产品形态

MultiSell 最终应该由四层组成。

### 1. 业务数据层

负责沉淀跨境电商运营的核心数据。

包括：

- 商品。
- SKU。
- 类目。
- 品牌。
- 供应商。
- 采购成本。
- 包装尺寸和重量。
- 物流供应商。
- 物流渠道。
- 报价规则。
- 平台。
- 平台费用规则。
- 订单。
- 库存。
- 运费快照。
- 利润测算。
- 操作日志。

这一层要求：

- 数据结构标准化。
- 历史数据可追溯。
- Agent 和人都能读取、写入和校验。

### 2. 业务工具层

负责把数据转化为可执行的业务判断。

包括：

- 商品资料完整性检查器。
- 物流数据完整性检查器。
- 运费计算器。
- 平台费用计算器。
- 上架前利润测算器。
- 上架建议器。
- 报价表导入器。
- 库存检查器。
- 订单利润分析器。

这一层要求：

- 每个工具都能独立运行。
- 输入输出清晰。
- 结果可解释。
- 适合被 Agent 调用。

### 3. Agent 协作层

这是 MultiSell 的核心差异。

未来系统不是让人手动点完所有页面，而是让不同 Agent 分工协作。

典型 Agent：

- 选品分析 Agent：判断候选商品是否值得进入测算。
- 商品资料 Agent：补齐标题、描述、规格、图片、类目。
- 物流测算 Agent：根据包装数据和目的国计算可用物流方案。
- 平台费用 Agent：根据平台、国家、类目计算佣金和费用。
- 利润分析 Agent：汇总成本、运费、平台费用、售价，计算利润率。
- 上架决策 Agent：给出上架建议和风险提示。
- 上架执行 Agent：在通过审批后推送到平台。
- 订单处理 Agent：后续处理订单、库存、发货和利润复盘。

这一层要求：

- Agent 不能绕过业务规则。
- Agent 的每一步操作都要有记录。
- 高风险动作必须由人审批。
- Agent 的结果必须可复核。

### 4. 人类控制层

人类不应该被迫处理所有细节。

人类主要负责：

- 设定目标。
- 查看结论。
- 审批关键动作。
- 处理异常。
- 调整策略。

例如：

```text
我要评估这 20 个商品是否适合上架到 Ozon 俄罗斯站。
```

系统和 Agent 应该完成：

- 检查商品资料是否完整。
- 检查尺寸重量是否完整。
- 计算物流成本。
- 计算平台费用。
- 测算售价和利润率。
- 标记高风险商品。
- 给出建议：可上架 / 需补资料 / 不建议上架。

## 第一阶段为什么选择“上架前经营决策”

Agent 协作平台不能一开始就做成通用超级平台。

原因：

- 范围太大。
- 验证困难。
- 容易变成很多页面堆叠。
- Agent 不知道围绕什么目标协作。

第一阶段必须选择一个具体切入口。

推荐切入口：

```text
商品上架前经营决策。
```

原因：

1. 业务价值明确：决定一个商品是否值得卖。
2. 数据链路完整：商品、成本、物流、平台费用、利润都能串起来。
3. Agent 价值明显：资料检查、费用计算、利润判断都适合 Agent 自动化。
4. 容易验收：最终结果就是能不能给出上架建议。
5. 后续可扩展：通过上架决策自然延伸到平台发布、订单、库存和报表。

## 第一可用版本定义

第一可用版本不是完整 Agent 平台。

第一可用版本的目标是：

```text
让系统能标准化完成商品上架前利润核算，并给出是否建议上架的判断。
```

### 第一版核心流程

```text
创建商品
→ 补齐商品资料
→ 补齐包装尺寸和重量
→ 维护供应商成本
→ 维护物流报价规则
→ 维护平台费用规则
→ 选择平台、国家、类目和预计售价
→ 系统计算运费
→ 系统计算平台费用
→ 系统计算预计利润和利润率
→ 系统给出上架建议
→ 人确认是否进入上架流程
```

### 第一版必须回答的问题

第一版必须让用户清楚回答：

1. 这个商品资料是否完整？
2. 这个商品是否具备运费计算条件？
3. 发到目标国家大概多少钱？
4. 在目标平台销售需要扣哪些费用？
5. 按预计售价能赚多少钱？
6. 利润率是否达到上架标准？
7. 是否建议上架？
8. 如果不建议上架，原因是什么？

定位：

第一阶段最核心页面。

输入：

- 商品。

- 平台。
- 国家。
- 类目。
- 预计售价。
- 采购成本。

## 标准化利润模型

第一版利润模型：

```text
销售收入 = 预计售价

商品成本 = 采购成本
物流成本 = 选定物流渠道运费
平台佣金 = 预计售价 × 平台佣金比例
支付手续费 = 预计售价 × 支付手续费比例
广告预留 = 预计售价 × 广告预留比例
固定费用 = 平台固定交易费 + 其他固定费用

总成本 = 商品成本 + 物流成本 + 平台佣金 + 支付手续费 + 广告预留 + 固定费用

预计利润 = 销售收入 - 总成本

利润率 = 预计利润 / 销售收入
```

第一版建议规则：

```text
利润率 >= 25%：建议上架
15% <= 利润率 < 25%：谨慎上架
利润率 < 15%：不建议上架
资料缺失：资料不完整
```

阈值后续应支持配置。

## Agent 在第一阶段应该怎么协作

第一阶段不做完整 Agent 平台，但要按 Agent 未来可用的方式设计。

### 商品资料 Agent

职责：

- 检查商品标题、描述、类目、图片、SKU 是否完整。
- 标记缺失项。
- 给出补齐建议。

### 物流测算 Agent

职责：

- 检查包装尺寸和重量。
- 调用运费计算器。
- 找出可用物流方案。
- 给出最便宜、最快、最均衡方案。

### 平台费用 Agent

职责：

- 根据平台、国家、类目匹配费用规则。
- 计算平台佣金、手续费、广告预留和固定费用。

### 利润分析 Agent

职责：

- 汇总成本、运费、平台费用和售价。
- 计算利润和利润率。
- 输出上架建议和风险原因。

### 人类审批

第一阶段高风险动作仍由人确认。

需要人确认的动作：

- 确认上架建议。
- 确认目标售价。
- 确认要发布的平台。
- 确认是否进入真实平台上架。

---

## 第一阶段不做什么

为了避免项目失控，第一阶段明确不做：

- 不做通用 Agent 平台。
- 不做真实平台自动发布闭环。
- 不接真实物流商 API。
- 不做复杂 BI 报表。
- 不做多仓库调拨。
- 不做售后退款退货完整流程。
- 不做财务对账系统。
- 不做广告投放系统。
- 不做全自动无人审批上架。

这些可以后续做，但不能抢第一阶段主线。

## 成功标准

第一可用版本成功，不是因为页面多，而是因为能跑通下面流程：

```text
选一个商品
→ 补齐商品资料和物流数据
→ 选择平台和国家
→ 输入预计售价
→ 系统自动算运费、平台费用、利润率
→ 系统给出上架建议
→ 人能据此决定是否上架
```

验收标准：

- 这个流程能在页面上跑通。
- 数据刷新后仍然存在。
- 计算公式可解释。
- 每个“不建议上架”都有原因。
- Agent 后续能基于这些数据继续扩展。

## 后续路线

### 阶段 1：上架前经营决策

目标：

- 建立商品上架前利润测算闭环。
- 建立平台费用规则。
- 建立上架建议状态。

### 阶段 2：Agent 辅助资料治理

目标：

- Agent 自动识别商品资料缺失。
- Agent 提出补齐建议。
- Agent 自动生成或优化商品标题、描述、关键词。

### 阶段 3：Agent 协作上架

目标：

- Agent 根据利润测算结果准备上架资料。
- 人审批后推送到平台。
- 系统记录上架过程和结果。

### 阶段 4：订单和履约 Agent

目标：

- Agent 处理订单、库存、物流方案和利润复盘。
- 异常订单交给人处理。

### 阶段 5：跨境电商 Agent 超级平台

目标：

- 多 Agent 协作完成跨境电商运营。
- 人类经营者主要负责目标、策略和审批。

## 后续所有 Agent 的约束

后续任何 Agent 做功能，都必须回答：

```text
这个功能是否服务于“上架前经营决策”？
这个功能是否让 Agent 未来更容易协作？
这个功能是否让人类更容易做最终判断？
```

如果答案是否定的，暂时不要做。
