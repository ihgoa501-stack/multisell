# 功能规格：凌镜 1688 采集助手重构

> 添加时间：2026-07-12
> 提出人：Owner
> 优先级：P0
> 状态：`implemented / automated_verified`（列表与详情插件测试50项通过；后端全量测试、96页前端生产构建、迁移全生命周期与路由安全通过）；设备配对、插件已连接、错误页提示和采集箱跳转已通过DevTools真实浏览器验收，真实1688列表批次和详情商品仍为`manually_verified: unknown`
> 产品边界：仅供 Owner 本人使用

阅读建议：Owner优先看第1、3、4.5、5、6、10、15和16节；第17—21节是给后续开发、测试和审查使用的实施契约，不要求Owner理解技术细节。

## 1. 一句话说明

Owner在1688首页/搜索页采集当前可见商品线索，或在商品详情页点击“采集到凌镜”保存更完整观察；商品默认进入Owner私人采集箱并当场显示结果，只有Owner决定继续研究时才关联已批准商品机会并进入受控草稿流程。

## 2. 为什么要重构

当前仓库已经有 Chrome 扩展、1688 页面解析、WebSocket 通信和后端采集代码，但实际使用流程不够完整：

- 插件存在页面加载后自动提取，不符合 Owner 主动点击采集；
- 插件可以显示本地解析结果，但结果没有形成清楚的“采集箱”体验；
- 采集结果、商品机会和现有1688草稿流程之间的关系不够直观；
- 登录、验证码、页面变化和后端断开等错误，需要 Owner 理解技术信息；
- 插件同时包含Ozon、淘宝和静默列表上传等能力，当前范围过宽；
- “解析到了页面”容易被误解为“已经保存到凌镜”。

本次重构参考成熟ERP和AI竞品公开资料中反复出现的使用方式，不把竞品宣传或未复现实测的效果写成已验证事实。

## 3. 产品定位

### 3.1 Owner 看到的产品

> 凌镜1688采集助手：Owner在1688列表页保存当前可见线索，在详情页补充更完整观察；决定继续研究时，再关联已批准商品机会并进入凌镜的受控货源草稿流程。

核心价值是：

- 少复制粘贴；
- 看见什么就采集什么；
- 采集结果集中管理；
- 页面信息自动整理；
- 能继续进入凌镜已有经营流程；
- 出错时不需要 Owner 调试。

### 3.2 后台必须保留的能力

采集结果仍须保留来源 URL、观察时间、原始信息和版本，避免把错误解析或 AI 整理结果冒充为页面事实。

证据追溯是后台可信基础，不作为插件面向 Owner 的主要宣传定位。

### 3.3 不是什么

第一版不是：

- 完整 ERP；
- 自动选品或爆品判断器；
- 多平台批量铺货工具；
- 自动发布、自动采购或库存同步工具；
- 面向外部客户的软件产品。

```text
在货源网站点击采集
→ 商品进入 ERP 采集箱
→ 检查和编辑
→ 认领到目标平台
→ 生成草稿或发布
```

### 4.4 AI/智能浏览器插件

`quoted`：公开资料显示，智能插件常见能力仍以页面入口、抽取、导入、研究叠层和状态同步为主。AI编辑、预测、监控和自动化经常由配套SaaS后台提供，不能全部算作插件本体能力。

| 产品 | 已确认的插件主能力 | 优点 | 不适合凌镜照搬的部分 |

| AutoDS Helper | 供应商页面单品/批量导入、选择店铺、默认进入 Draft，也可配置直接发布 | 页面入口和备用弹窗清楚；默认草稿；故障建议具体 | 直接发布、多店、履约和买家地址范围过宽；AI编辑实际属于后台增强 |
| DSers | AliExpress 页面按钮、单品/批量导入、进入 Import List、编辑后推送店铺 | 页面原位按钮；统一待处理区；编辑后再继续 | 采集、履约和订单耦合；1688与AI能力的详细手册证据不足 |
| AliPrice/AiPrice | 图片悬浮、截图/上传找同款、图片视频下载和图片翻译 | 页面内找同款入口自然；素材工具实用 | 没有确认的ERP式采集箱和受控后续流程；工具容易堆叠 |
| ZIK Analytics | eBay 页面底部研究条、侧栏、竞品数据和收藏同步 | 不离开页面；状态和免费/付费边界清楚 | 估算销量和收入容易被误当事实；不是1688货源采集器 |
| Sell The Trend | 页面抽取后进入后台AI评分，再推送店铺和履约 | 采集到后台的链路清楚 | “winning product”和预测口径不透明；自动发布与履约风险过高 |
| Dropship.io | Shopify商品、店铺和广告研究叠层，一键保存或导入 | 页面即时情报和后台同步 | 估算销售数据风险高；不是供应商页面事实采集 |

### 4.5 凌镜采用什么

采用成熟 ERP 的主流程：

- 1688 页面一键采集；
- 凌镜采集箱；
- 商品信息预览和编辑；
- 重复提示并保留再次观察的版本基础；
- 后续按需要关联选品任务；
- 进入现有 1688 草稿流程。

后续采用 AI 产品的一部分辅助体验：

- 自动整理杂乱标题；
- 自动总结商品卖点；
- 自动整理 SKU；
- 标出缺失信息；
- 比较本次商品与历史采集的变化。

AI 整理结果必须与原始采集信息分开，Owner 可以修改或不采用。AI 不进入第一版采集成功的关键路径。

### 4.6 外部优秀产品组合后的目标体验

凌镜不完整复制任何一家，而采用各自最成熟的一段：

- 学DSers：在1688商品页原位提供单一采集按钮；
- 学Importify：点击后立即在当前页看到采集摘要；
- 学AutoDS：结果有明确且唯一的默认落点；
- 学Matrixify：逐项说明成功、警告和失败，并支持修正后重试；
- 学Shopify Collective：采集、编辑、关联任务和发布是不同动作；
- 学店小秘：重复商品由Owner明确查看或追加观察；
- 学BigSeller：采集记录保留来源、时间和状态；
- 学妙手：原始公共信息与后续用途层分开；
- 学芒果店长：1688价格区间和SKU结构清楚展示；
- 学Monica/HARPA/Glasp：页面读取由Owner明确触发，轻侧栏不打断浏览，结果可回原文核对，AI建议可以撤销。

详细外部研究：

- [优秀商品采集／导入插件研究](../research/excellent-import-plugins-2026-07-12.md)
- [优秀AI浏览器插件交互研究](../research/excellent-ai-browser-extensions-2026-07-12.md)

最终交互原则：正常商品真正一键保存，侧栏负责即时反馈而不是增加必填表单；只有商品身份无法确认、重复商品出现关键变化或结果待对账时，才要求Owner额外决定。

## 5. 第一版完整流程

```text
Owner 登录凌镜
→ 在1688首页/搜索页主动采集当前可见线索，或打开商品详情页点击“采集到凌镜”
→ 插件显示“正在读取 → 等待确认”以及字段来源、缺失或解析失败
→ Owner确认后显示“正在保存”
→ 商品自动进入Owner私人采集箱，状态为未验证线索
→ 侧栏显示“已保存”、记录编号、查看采集箱和继续浏览
→ 凌镜提示重复商品、字段缺失和历史变化
→ Owner 检查或编辑商品信息
→ 决定继续研究时，关联一个选品任务
→ 需要继续时，进入现有 1688 草稿流程
```

### 5.1 尚未关联选品任务时

商品可以保存到Owner私人采集箱，但固定标记为`unverified_lead`：它只是Owner从1688保存的未验证页面线索，不是商品机会、经营证据、可信货源或可上架草稿。

未关联选品任务的商品可以查看、整理、归档或删除；不能转入草稿、审批、发布、采购或其他经营状态。经营闸门从“采集前”移动到“进入待研究商品/草稿前”。

## 6. 第一版功能范围

### P0-1：安装和连接

- 插件可以通过清楚的安装说明加载；
- Owner 在凌镜登录后完成插件连接；
- 不要求复制 JWT、Token 或打开开发者工具；
- 中文显示未连接、连接中、已连接、登录过期和服务不可用；
- Chrome 或后端重启后可以恢复连接。

### P0-2：1688 页面主动采集

- 第一版支持1688首页、搜索结果页和商品详情页；
- 首页和搜索页支持勾选当前可见商品后“采集选中”，以及由Owner明确触发的“采集本页”；
- “采集本页”只处理当前已经加载、能够确认精确offer ID和详情链接的商品，不自动翻页、不采完整店铺、不设置固定数量；
- 列表页只保存能可靠取得的线索字段；需要SKU、阶梯价、MOQ和供应商详情时，再进入详情页补充采集；
- Owner 点击后才采集和上传；
- 普通浏览时不自动上传；
- 无可靠商品链接时明确提示本页没有可采集商品；
- 不要求先在凌镜填写商品 URL。

### P0-3：采集字段

第一版采集：

- 商品标题；
- 1688 商品 ID；
- 商品 URL；
- 当前价格或价格区间；
- 起订量；
- 供应商名称和可取得的供应商身份；
- 商品主图；
- SKU/规格、对应价格和可取得的库存；
- 商品属性；
- 页面观察时间。

页面取不到的数据必须显示“未取得”，不能用默认值或 AI 猜测冒充原页面数据。

列表页报价、详情页阶梯价、SKU价格和Owner整理值必须保留各自来源，后取得的数据不能静默覆盖先前观察。列表页供应商、MOQ或SKU没有可靠页面结构时保持`unknown`。

### P0-3.1：批量操作结果

- 批量采集按商品逐项返回成功、重复、失败或待确认，不能用一个“全部完成”掩盖部分失败；
- 同一offer只生成一个商品主体，重复采集按再次观察处理；
- 批量请求采用Owner可见的间隔和随机抖动，支持中途停止；
- 页面滚动、搜索切换和虚拟列表更新后重新识别商品，但不自动提交；
- 其他ERP插件注入的链接、价格、供应商和促销文案不得参与凌镜解析。

### P0-4：页面内即时反馈

Owner点击后，侧栏至少显示：

- 标题；
- 价格；
- 起订量；
- 供应商；
- 图片数量；
- SKU 数量；
- 缺失的重要字段。

正常商品先显示一次轻量预览，由Owner点击“确认保存”；提交前按第20.8节重新读取关键摘要。侧栏必须依次区分“正在读取”“等待确认”“正在保存”“已保存”；只有服务端返回记录编号后才能显示已保存。本条以20.6和20.8的安全契约为最终裁决。

商品身份无法确认时不保存；同一商品已经存在且检测到关键变化时，侧栏展示差异，由Owner选择查看已有记录或保存本次新观察。

### P0-5：凌镜采集箱

采集成功后，商品进入凌镜采集箱。采集箱支持：

- 查看最近采集商品；
- 按状态筛选；
- 查看原始 1688 链接；
- 查看采集时间；
- 查看采集是否完整；
- 查看是否重复；
- 查看是否已关联选品任务；
- 归档或删除尚未进入受控经营事实链的私人收藏；
- 进入商品检查和编辑页面。

### P0-6：重复识别

- 同一 1688 商品重复采集时明确提示；
- Owner 可以选择查看已有记录或保存一次新的观察；
- 不因为重复点击产生多条无法解释的完全相同记录。

底层保留多次观察及版本关系；完整的价格、起订量、供应商、SKU和图片变化时间线属于 P1。

### P0-7：检查和编辑

Owner 可以编辑用于后续经营的工作副本，例如：

- 整理后的商品名称；
- 自己的备注；
- SKU 名称和选择；
- 准备采用的图片；
- 需要进一步核实的问题。

原始采集快照不能被编辑覆盖。编辑结果与来源页面信息分开保存。

### P0-8：关联选品任务

- 采集进入私人采集箱时不要求预先选择任务；
- Owner决定继续研究时，可以关联已有选品任务；
- 只有一个可用任务时可以默认选中，但必须展示给Owner确认；
- 多个任务时由Owner选择；
- 后端重新验证任务属于同一Owner，并满足进入待研究/草稿所需的经营闸门；
- 不符合条件时保留私人收藏，但阻止进入受控经营流程，并明确说明原因；
- 授权对象是最新`selected`市场决定下仍有效、经Owner批准的`product_opportunity_id + opportunity_decision_id`；`experiment_id`只能作为可选trace，不能授权。

### P0-9：进入现有 1688 草稿流程

- 关联选品任务并满足现有条件后，可以进入当前 `sourcing1688` 草稿流程；
- 继续使用现有编辑、审批、成本、图片、合规和渠道规则；
- 转换后仍保持 `product_listing.status=draft`；
- 插件本身不能发布商品；
- 真实发布继续使用独立 Owner 审批和执行流程。

### P0-10：中文错误和恢复提示

至少覆盖：

| 情况 | 插件告诉 Owner 什么 |
|---|---|
| 凌镜未连接 | 如何登录或重新连接 |
| 当前页没有可靠商品 | 在首页/搜索页等待商品卡加载，或打开商品详情页后重试 |
| 1688 未登录 | 登录 1688 后重试 |
| 出现验证码 | 人工完成验证后重试 |
| 页面信息不完整 | 哪些字段未取得；可以先收藏还是必须重新采集 |
| 页面结构无法识别 | 停止重复点击，更新解析器 |
| 商品已经采集 | 查看已有记录或保存新观察 |
| 后端不可用 | 本次是否保存，恢复后怎样处理 |
| 登录过期 | 重新登录凌镜 |
| 不能关联选品任务 | 私人收藏仍保留，并说明缺少哪个经营前置条件 |

任何错误都不能只显示英文报错或要求 Owner 查看控制台。

## 7. P1：AI辅助和增强功能

以下能力在 P0 主闭环真实可用后再实施。它们属于凌镜后台工作台，不应全部塞进浏览器浮层：

- 标题整理；
- 卖点摘要；
- SKU 名称和结构整理；
- 翻译建议；
- 缺失和冲突说明；
- 历史采集变化视图；
- 更完整的工作副本编辑；
- 供应商补充信息。

调研新增的优先顺序：

1. **采集质量中心**：按字段显示来源层级、观察时间、缺失、冲突和重新补采入口；
2. **SKU整理工作台**：检查颜色×尺码×款式组合、缺失价格/库存和目标渠道映射；
3. **货源变化监控**：对Owner明确关注的商品检查价格、MOQ、SKU、库存声明和下架状态，只提醒，不自动覆盖草稿；
4. **素材管理**：区分主图、SKU图、详情图和视频，保存来源与权利状态后再进入图片处理；
5. **成本与草稿联动**：复用现有采购价、运费、汇率、平台费、利润、图片、合规和草稿审批能力。

截至2026-07-13，上述五项已进入代码并通过自动验证：质量中心区分列表/详情/受控观察并显示来源、缺失和历史变化；SKU工作台展示观察组合、缺价格/库存和三段映射；货源关注通过Owner浏览器新观察生成只读提醒；素材资产保存分类、SKU绑定、处理版本和适用市场/渠道的权利证据；草稿审批必须显式冻结整数精确成本版本及内容哈希。视频没有受控处理器时固定为blocked，不伪装成已支持。

AI 不应仅因竞品营销页写有“AI”就进入 P0。只有能够说明输入、输出、失败处理和 Owner 实际收益时才实现。

### 7.1 AI边界

P1 可以使用 AI 帮助整理，但不让 AI 改写事实：

| AI 能做 | AI 不能做 |
|---|---|
| 整理标题 | 把整理后的标题冒充 1688 原标题 |
| 总结卖点 | 宣称这些卖点已经得到消费者验证 |
| 整理 SKU 名称 | 编造不存在的规格和库存 |
| 标出缺失字段 | 用推测补齐缺失字段 |
| 总结商品变化 | 自动判断应该采购或发布 |
| 提醒需要核实的问题 | 自动通过经营闸门 |

AI 功能不可用时，基础采集、采集箱和人工编辑仍必须可用。

## 9. 什么是好，什么是不好

### 好

- Owner 在 1688 看见商品后可以直接采集；
- 采集后进入清楚的采集箱，而不是散落在不同模块；
- 原始信息和编辑结果分开；
- 重复和缺失信息清楚；
- 不懂调试也能处理常见错误；
- 可以顺利关联已批准商品机会并进入草稿流程；
- AI 帮助整理，但不伪造事实；
- 没有未经批准的发布和其他外部写入。

### 不好

- 功能很多，但单个商品不能从 1688 进入凌镜；
- 采集成功后找不到商品；
- 页面解析成功被误称为后端保存成功；
- 同一个商品重复生成大量记录；
- 编辑后无法追溯原页面；
- AI 把推测写成真实商品字段；
- 要求 Owner 复制 Token、看日志或打开控制台；
- 为了对标 ERP，一次加入批量铺货、订单和库存系统。

## 10. 验收方式

### 10.1 主闭环验收

主闭环需要一个真实列表批次和一个Owner实际准备研究的真实1688详情商品：

10. 全程不打开开发者工具，不复制凭证；
11. 插件没有自动发布或修改任何外部平台数据。

真实列表批次和真实详情商品都完成上述流程，才能证明第一版主闭环成立；仅完成详情商品只能证明详情入口。

## 17. 开发前必须确定的实施契约

本节用于消除“产品方向正确，但不同开发者会做出不同结果”的问题。以下为当前推荐方案；实施审计发现现有代码已有等价能力时，应优先复用而不是另建一套。

### 17.1 插件交互形态

第一版推荐三个界面各司其职：

| 位置 | 作用 | 不承担的责任 |
|---|---|---|
| 1688 首页/搜索页列表面板 | 勾选当前可见商品、“采集选中/采集本页”、逐项结果与停止 | 不自动翻页、不采完整店铺、不承担详情字段补全 |
| 1688 商品页按钮 | 主入口“采集到凌镜” | 不自动发布，不在页面内堆满ERP功能 |
| 轻量侧栏 | 显示读取/预览确认/保存状态、关键字段摘要和最终结果 | 不成为完整商品编辑器 |
| 插件弹窗 | 显示连接状态、当前页面是否支持、最近一次结果，并提供备用采集入口 | 不复制完整采集箱 |
| 凌镜采集箱 | 查看原始快照、工作副本、重复状态和后续操作 | 不直接绕过草稿审批发布 |

第一版保留两种语义明确的主动入口：列表页保存可见商品线索，详情页保存更完整的页面观察。右键菜单、图片悬浮找同款、自动翻页和整店入口暂不增加，避免Owner误解数据完整度或采集范围。

### 17.2 复用现有 `sourcing1688`，不新建第二套商品事实

开发前必须先核对现有对象是否已经能承担以下职责：

- 采集商品主体；
- 原始快照；
- 同款和重复识别；
- 多次观察与变化记录；
- 供应商、SKU和图片；
- `editing → pending_approval → approved_draft` 草稿状态；
- 最新Owner市场决定、已批准商品机会和可选trace关联。

推荐原则：

- “采集箱”优先是现有 `sourcing1688` 数据的 Owner 视图，不默认新建独立商品池；
- 如果现有模型缺少待检查状态，只新增最小状态或关联，不复制整个生命周期；
- 旧的普通 candidate 自动保存路径不得继续作为本插件的落点；
- 数据迁移前必须列明旧插件记录如何读取、保留或标记为历史来源。

### 17.3 P0字段判定矩阵

| 字段 | 作用 | 私人采集箱 | 进入待研究/草稿前 |
|---|---|---|---|
| 1688 商品ID | 商品身份 | 缺失或冲突时阻止收藏 | 必须有效 |
| 规范URL | 来源和去重 | 缺失或冲突时阻止收藏 | 必须与商品ID一致 |
| 原始标题 | 页面识别 | 缺失时阻止收藏 | 必须存在；AI标题另存 |
| 当前价格或价格区间 | 初步成本线索 | 允许unknown并突出提示 | 必须取得可靠口径，否则阻止进入 |
| 起订量 | 供应可行性 | 允许unknown并突出提示 | 必须取得，否则阻止进入 |
| 供应商名称/业务身份 | 来源线索 | 名称可见但稳定身份缺失时允许unknown | 草稿前必须补齐现有规则要求的身份 |
| 主图 | 后续检查 | 允许unknown | 由现有图片规则裁决 |
| SKU/规格 | 变体和成本 | 无规格、unknown、parse_failed必须区分 | 页面有SKU时必须可靠取得 |
| 库存 | 参考信息 | 允许unknown | 由现有草稿规则裁决 |
| 商品属性 | 后续整理 | 允许unknown | 由现有草稿规则裁决 |
| 客户端观察时间 | 页面观察上下文 | 必须提供 | 不能覆盖服务端时间 |
| 服务端接收时间 | 审计与对账 | 服务端必须生成 | 不能由插件提供 |

具体阻断规则必须通过公开接口测试，而不是只写在页面组件中。

### 17.4 成功状态必须分层

建议统一状态：

```text
page_supported
→ reading
→ submitting
→ saved
→ unverified_lead
```

异常状态：

```text
blocked
failed
reconcile_required
```

含义：

- `preview_ready`：插件读到了可展示字段，尚未保存；
- `submitting`：请求已经发出，结果尚未确认；
- `saved`：服务端已持久化并返回服务器记录编号；
- `blocked`：前置条件不满足，明确没有保存；
- `failed`：服务端或解析明确失败，明确没有保存；
- `reconcile_required`：请求可能已保存但响应丢失，必须查询，不能盲目重提。

只有 `saved` 可以显示“已保存到凌镜”。页面解析成功、WebSocket发送成功和HTTP接收成功都不能单独称为保存成功。

### 17.5 请求身份、幂等和对账

推荐协议：

- Owner点击确认时由插件生成随机 `request_id`；
- 服务端以 `owner_id + request_id` 建立唯一约束；
- 第一次提交同时携带结构化数据哈希；
- 相同request_id和相同哈希重复提交时，返回第一次结果；
- 相同request_id但哈希不同，必须冲突失败；
- 同一个1688商品在新的真实观察时间可以建立新版本，但不能复用旧request_id；
- 插件保存尚未完成的request_id，以适应Manifest V3后台休眠和Chrome重启；
- 超时后先查询request_id状态，再决定显示已保存、明确失败或允许重试。

建议最小状态查询：

```text
GET /api/v1/sourcing-1688/collection-requests/:request_id
```

返回至少包含：状态、是否已保存、服务器记录ID、失败原因和下一步。最终接口名称以现有路由审计为准。

### 17.6 页面主动采集接口

现有服务端指定URL的受控采集与新流程方向不同。推荐把新流程拆成两个清楚的公开能力：

1. 提交Owner当前页面的私人收藏；
2. 在Owner决定继续研究时查询并关联可用选品任务。

选品任务查询至少返回：

- product_opportunity_id和opportunity_decision_id；
- Owner可识别的商品机会名称；
- 国家/地区、目标消费者和销售渠道；
- 最新Owner市场决定与机会批准状态；
- 是否允许接收1688货源证据；
- 被阻止时的人话原因。

`experiment_id`如存在只作为可选trace返回，不能决定任务是否可选。

私人收藏提交接口必须重新验证：

- Owner身份和权限；
- 商品URL与ID是否一致；
- 必需字段是否满足；
- request_id是否重复；
- 原始载荷哈希是否一致。

关联选品任务和转草稿时，后端必须另外验证任务仍属于同一Owner、状态和经营闸门仍有效。查询到可用任务不构成最终授权，实际关联和转换时必须再次裁决。

### 17.7 登录、配对和撤销

“不复制Token”必须落实为可验收协议：

- Owner在已经登录的凌镜页面发起插件配对；
- 页面显示正在连接的是哪个凌镜环境和哪个浏览器；
- 配对需要一次Owner明确确认；
- 服务端签发限Owner、限插件用途、短时且可撤销的凭证；
- 插件不得保存凌镜密码或1688密码；
- 敏感凭证不长期放在`storage.local`；
- 凌镜退出登录、Owner撤销或凭证过期后，插件必须停止保存；
- 设置页提供“断开此浏览器”；
- 本地和生产环境必须明显区分，避免把测试数据写入真实环境；
- 生产只允许HTTPS/WSS，本机开发例外。

多浏览器配置或多设备同时连接时，每个连接应有独立身份和撤销能力，不能共用一个无法区分的长期Token。

### 17.8 页面身份和观察时间

必须定义唯一的规范化规则：

- 允许的host和商品详情路径；
- 如何去除追踪参数；
- 如何处理页面重定向；
- 商品ID从URL、DOM和页面结构化数据取得时的优先级；
- 多个来源冲突时阻止保存并保留失败原因；
- 同时打开多个1688标签页时，只采集Owner当前确认的标签页；
- 预览后页面发生跳转或商品变化时，提交前重新核对身份。

时间至少区分：

- `client_observed_at`：浏览器观察时间；
- `server_received_at`：服务端接收时间；
- `saved_at`：持久化完成时间。

客户端时间异常不能覆盖服务端时间，也不能单独证明真实观察时间准确。

### 17.9 原始证据与隐私边界

开发前要按入口区分原始证据，避免默认保存整页所有内容：

- 插件私人收藏只上传固定schema的有限结构化页面观察，不上传DOM片段、整页HTML或页面脚本；
- 后续已授权任务的`controlled_fetch`可保存实际响应字节，以及支持字段追溯所需的有限、脱敏DOM片段；
- 不保存密码、Cookie、聊天、收货地址等无关内容；
- 设定单次载荷体积上限；
- 对原始字节计算SHA-256，不能先重排JSON再声称是原始哈希；
- 失败日志只保存排错所需信息；
- 明确Owner读取权限、保留期限和备份范围；
- 页面截图如果未来需要，应单独定义，不默认进入P0。

### 17.10 解析器和页面变化

- 每次结果携带 `extension_version`、`schema_version` 和 `parser_version`；
- 页面解析与插件通信分离；
- 对真实页面结构建立脱敏fixture回归测试；
- 页面关键结构无法识别时失败关闭；
- 区分“页面没有SKU”和“解析器没有取得SKU”；
- 价格必须区分固定价、区间价、阶梯价和规格价；
- 页面需要登录、验证码或地区条件时明确提示，不能误判为商品没有数据；
- 解析器版本过旧时提示更新，不让Owner无限重试。

### 17.11 并发、休眠和恢复

- 同一标签页连续点击时按钮进入处理中，防止并发提交；
- 不同标签页的请求必须以request_id和tab identity隔离；
- 关闭侧栏、关闭标签页或Chrome重启后，可以查询未完成结果；
- 后端重启后仍能按数据库记录对账；
- 不依赖Manifest V3 Service Worker永久驻留；
- 重试采用有上限的退避，不无限循环；
- Owner取消操作后，未提交数据不得被后台继续上传。

### 17.12 内容安全

- 1688页面属于不可信输入；
- 页面标题、描述、属性和供应商内容在插件及凌镜显示时必须转义；
- 不执行页面提供的脚本、HTML事件或远程代码；
- 插件不使用`eval`、`new Function`或远程托管脚本；
- content script消息必须校验发送者、消息类型和request_id；
- 服务端不能因为消息来自已安装插件就跳过Owner、权限和业务验证；
- Manifest只声明必要域名，不使用`<all_urls>`；
- 日志和错误信息不能回显完整凭证或原始敏感载荷。

## 18. 还容易遗漏的问题

### 18.1 价格不是单一事实

1688价格可能受登录账号、地区、购买数量、SKU、活动、会员等级和代发/批发模式影响。插件必须显示自己实际取得的价格口径，不能把页面某个数字统一叫“采购成本”。最终成本仍需运费、税费、包装、汇率和渠道费用证据。

### 18.2 库存和销量可能只是页面展示值

库存、成交量和供应商评分可能动态变化，也可能不是可独立核验的真实库存或销量。它们只能记录为页面观察，不能自动升级为供应商履约能力或市场需求证据。

### 18.3 图片可采集不等于可使用

插件可以保存图片URL或预览，但不能因此声明Owner拥有版权、商标权或渠道使用权。进入草稿流程时仍需现有图片权利检查和实际处理记录。

### 18.4 商品页可能在预览与提交之间变化

动态页面可能切换SKU、数量或价格。提交前必须重新计算商品身份和关键字段摘要；商品ID、URL、标题、供应商、价格、起订量或已选SKU发生第20.8节定义的变化时，必须阻止或要求Owner重新确认，不能保存旧预览配新页面。

### 18.5 1688规则和反自动化限制

是否允许特定采集方式、页面结构、登录状态和访问频率可能变化。当前公开资料不足以证明任何长期稳定契约，相关状态为`unknown`。出现验证码、访问阻断或账号风险时应停止自动重试，由Owner人工判断。

### 18.6 旧插件和旧数据兼容

当前工作区已有插件和采集链改动。实施前必须：

- 列出旧消息协议和新协议差异；
- 处理旧版插件仍连接后端的情况；
- 拒绝不支持的schema版本并给出升级提示；
- 保留旧快照的真实来源等级，不静默升级为新受控采集；
- 不把历史自动采集记录混入新采集箱并冒充P0结果。

### 18.7 删除与归档

ERP竞品存在不可恢复清空功能，这是凌镜不应照搬的部分。P0不提供批量清空。尚未关联选品任务、且未进入任何受控经营事实链的私人收藏可以归档或删除；一旦进入任务、草稿、审批、发布或审计事实链，只能按治理规则归档，不得由普通采集箱操作删除。

### 18.8 无障碍和可见反馈

侧栏和弹窗需要：

- 清楚的加载、成功、阻止和失败状态；
- 不能只用颜色区分结果；
- 中文按钮和错误信息；
- 长标题和大量SKU不会挤坏界面；
- 页面缩放或窄窗口下仍能确认和取消；
- 操作完成后提供前往凌镜采集箱的明确入口。

### 18.9 监控与排错由系统承担

Owner不调试不代表系统不留证据。每次请求应能通过request_id串联：

```text
插件点击
→ 页面解析
→ 提交
→ 服务端校验
→ 数据库保存
→ 采集箱展示
```

内部日志要能定位失败环节，但Owner界面只显示人话、是否保存和下一步。

### 18.10 灰度、回退和停止条件

第一版应有简单开关允许停用新主动采集入口并回退到只读状态，但不能回退到静默自动采集。

出现以下任一情况，应停止扩大功能并先修复：

- 采错商品或串到错误Owner、市场决定或商品机会；
- 页面失败却显示已保存；
- 原始值与工作副本无法区分；
- 重复点击产生无法解释的重复记录；
- 登录或凭证无法安全撤销；
- 页面改版后仍静默输出错误字段；
- Owner必须打开控制台才能恢复；
- 尚未跑通真实列表页和真实详情页，就继续增加整店采集、搜同款或自动发布。

## 19. 实施顺序建议

```text
现有代码与数据模型审计
→ 决定复用对象和迁移边界
→ 固定消息/API/状态/幂等契约
→ 实现插件连接、列表页主动入口和商品页主入口
→ 实现预览和私人采集箱保存
→ 实现选品任务关联和经营闸门
→ 实现最小采集箱视图与工作副本
→ 接回现有1688草稿流程
→ 收紧权限并删除静默自动采集
→ 自动测试与干净Chrome验证
→ 一个真实列表批次和一个Owner真实详情商品共同完成插件主闭环
→ 新事实审计
→ 再决定是否启动P1 AI整理
```

任何阶段都不得以页面数量、代码量或功能数量替代真实闭环进展。

## 20. 最终缺口审查后的补充裁决

### 20.1 页面事实的真实性上限

插件采集到的是“该Owner浏览器在该时间看到的1688页面声明”，不是供应商履约、真实库存或可成交价格的独立证明。

推荐记录：

- “Owner点击过采集、服务端收到并保存过这些字节”可以记录为系统中的 `actual` 操作事实；
- 商品标题、价格、库存、销量、供应商介绍等页面内容固定按 `quoted` 保存；
- 原始字节SHA-256只能证明保存后是否变化，不能证明1688页面内容本身真实；
- Owner后续人工核对可以证明“页面与采集结果一致”，但不能把供应商声明升级为已履约事实；
- 真实成交价、供货能力和商品质量仍需要订单、沟通、样品或履约证据。

### 20.2 P0字段只允许一个确定结果

为避免不同实现者自行决定，P0采用以下规则：

| 情况 | 服务端采集箱 | 失败记录 | 草稿转换 |
|---|---:|---:|---:|
| 商品ID或规范URL缺失/冲突 | 不保存 | 保存 | 阻止 |
| 原始标题缺失 | 不保存 | 保存 | 阻止 |
| 价格/价格区间无法可靠取得 | 保存为unknown并突出提示 | 不需要 | 阻止，直到补齐可信来源 |
| 起订量无法可靠取得 | 保存为unknown并突出提示 | 不需要 | 阻止，直到补齐可信来源 |
| 供应商稳定业务身份缺失 | 保存展示名称并标记unknown | 不需要 | 由现有供应商规则阻止，直到补齐 |
| 页面确认没有SKU | 保存并标记无SKU | 不需要 | 允许继续检查 |
| 页面存在SKU但解析失败 | 保存为parse_failed并突出提示 | 同时留解析失败记录 | 阻止 |
| 主图缺失 | 保存并标记unknown | 不需要 | 草稿阶段继续阻止，直到图片要求满足 |
| 库存或普通属性缺失 | 保存并标记unknown | 不需要 | 由现有草稿规则裁决 |

“失败记录”只证明采集尝试发生；私人采集箱商品也只是未验证线索，两者都不生成商品机会。

真实验收改为：所有已取得字段与当时页面逐项一致；未取得字段必须符合上表状态。无SKU商品不要求凭空出现SKU。

### 20.3 同一商品跨选品任务模型

推荐业务模型：

- 规范化1688商品身份在Owner范围内唯一；
- 同一商品可以服务多个已获准选品任务；
- 每个任务通过独立关联表达用途和状态，不能复制一份无法追溯的商品主体；
- 每次真实重新采集产生一次Owner级观察版本；观察记录request_id，关联任务时建立商品机会授权关系，`experiment_id`仅可选trace；
- 任务A已有该商品时，在任务B关联应提示“商品已存在，将新增任务关联”，不能误报为禁止重复；
- 删除某个任务关联不能删除其他任务、原始观察或已进入草稿的事实。

最终数据库形态必须先与现有`sourcing1688`模型对照；如果当前模型无法表达，不得在没有迁移方案时直接实现前端行为。

### 20.4 草稿转换也必须幂等

采集幂等和草稿转换幂等是两件事：

- 转草稿时生成独立的 `conversion_request_id`；
- 同一采集箱商品、实验和目标草稿只能存在一个有效转换链；
- 双击、超时或重试时返回已有草稿，不新建第二份；
- 转换结果必须可查询；
- 部分成功或结果不确定时进入对账状态，不能自动再次创建；
- 已转换记录明确关联现有draft_id和后续审批链。

### 20.5 三类哈希分别定义

不得用一个“SHA-256”同时代表三种不同对象：

1. `raw_evidence_sha256`：对插件提交的有限原始证据原字节计算；
2. `structured_data_sha256`：对固定schema、UTF-8、稳定字段顺序和稳定SKU/图片顺序的规范化结构计算；
3. `request_envelope_sha256`：对Owner、request_id、版本和结构化数据组成的固定采集请求信封计算；后续任务关联使用独立操作哈希和幂等键。

相同request_id只有在request envelope哈希相同时才可幂等返回原结果。原始证据哈希不能证明来源真实，只证明服务端保存的字节是否变化。

### 20.6 P0通信采用HTTPS请求，不依赖常驻WebSocket

Manifest V3后台不保证长期运行。推荐：

- 预览在当前content script和页面轻量面板内完成；
- 私人收藏提交、选品任务查询/关联和结果查询使用HTTPS API；
- WebSocket只保留给现有兼容能力，不作为P0保存成功的唯一确认通道；
- 未完成请求只持久化request_id、状态、目标环境和必要的非敏感摘要；
- 不在后端不可用时长期缓存完整商品载荷；恢复后要求Owner重新打开页面并确认；
- 页面轻量面板使用content script隔离环境实现，不把Chrome Side Panel API作为P0依赖；
- popup负责连接状态和备用入口，不能显示另一个标签页的“最近结果”冒充当前页结果。

### 20.7 配对协议的最低要求

实施方案必须同时满足：

- 凌镜已登录页面产生一次性nonce；
- nonce短时有效、只能使用一次并绑定目标环境；
- 插件响应时携带稳定extension identity和随机device_id；
- Owner在凌镜页面明确确认本次浏览器连接；
- 服务端签发限 `sourcing1688.collect`、读取本人采集结果和只读选品任务查询的插件凭证；
- access凭证短时；长期恢复凭证如果存在，必须可按设备撤销并限制用途；
- Chrome重启后可以通过设备凭证恢复，但凌镜退出、Owner撤销或账号禁用后服务端拒绝；
- 恶意普通网页不能通过任意`window.postMessage`诱导配对；
- 开发、验收和生产环境使用不同的可见标识和凭证。

具体有效期由认证架构审计后确定，不在缺乏证据时填写任意天数。

### 20.8 动态页面提交前重新确认

提交前重新读取关键摘要并与预览比较：

- 商品ID或规范URL变化：立即阻止；
- 标题或供应商身份变化：重新展示预览并确认；
- 价格、起订量、当前选择SKU变化：重新展示预览并确认；
- 页面仍在加载、SKU异步价格尚未稳定：等待明确完成信号或超时失败；
- 页面跳到相似商品、下架占位或风控页：作为身份失败，不当作普通字段缺失；
- 登录弹层、验证码或iframe遮挡关键内容：停止读取并提示人工处理。

“变化明显”不再作为验收用语，以上字段变化就是确定触发条件。

### 20.9 后端不可用和取消语义

- 后端不可用时不保存完整商品载荷到长期本地存储；
- 插件显示“未保存”，Owner恢复连接后重新打开页面采集；
- 提交前取消：清除本次预览和临时数据，不上传；
- 提交后关闭面板或标签页：不等于撤销服务端请求；下次按request_id查询；
- 服务端已经保存后不能通过插件“取消”删除，只能进入现有归档/治理流程；
- `reconcile_required`不能显示“已取消且未保存”；
- 临时页面片段在成功、明确失败、取消或超时终结后清除。

### 20.10 图片、URL和载荷限制

如果后端需要抓取图片，必须使用现有受控图片处理入口并防止服务端请求伪造（SSRF）：

- 只允许批准的HTTPS图片host；
- 禁止私网、localhost、云元数据地址和重定向到禁止地址；
- 限制图片数量、单图大小、总大小、Content-Type和超时；
- 拒绝伪装成图片的HTML/SVG脚本内容；
- 图片URL中的签名、账号和追踪参数不得原样进入公开展示或日志；
- 同时限制SKU数量、属性数量、字符串长度、DOM片段和请求总大小；
- 超过上限必须明确失败或截断为unknown，不能拖垮插件和后端。

具体上限根据真实页面和现有图片处理能力测量后确定，不填写没有依据的数字。

### 20.11 旧版本切换契约

开发前必须形成一张版本兼容表：

| 项目 | 必须明确 |
|---|---|
| 插件版本 | 服务端支持的最低和最高版本 |
| schema版本 | 新旧消息如何区分和拒绝 |
| 旧插件连接 | 只读、兼容期还是要求升级 |
| 历史自动采集数据 | 隐藏、历史分区或迁移，不得冒充新受控记录 |
| 灰度回退 | 新记录是否可由旧代码安全读取 |
| 紧急停用 | 谁能操作、是否审计、Owner看到什么 |

回退只能关闭新入口或进入只读，不能恢复静默自动采集。

### 20.12 采集箱完整状态机

推荐补齐：

```text
unverified_lead
→ needs_review
→ reviewed
→ ready_for_draft
→ converting
→ converted_to_draft
```

旁路状态：

```text
blocked
conversion_failed
reconcile_required
archived
```

规则：

- 原始或工作副本关键内容改变后，`reviewed`退回`needs_review`；
- 选品任务资格后来失效时，保留私人收藏但任务关联退回阻止状态，不能转草稿；
- 新观察不自动覆盖已审核工作副本，必须显示差异并重新确认；
- 转换过程加乐观锁和转换幂等；
- `converted_to_draft`必须一对一指向现有draft；
- 归档可以恢复，但不能删除已进入实验、草稿、审批或审计链的数据；
- 每个状态转换明确操作者、时间、原因和审计记录。

## 21. P1工程增强与外部未知

### 21.1 P1工程增强

- content script保持isolated world；确需读取页面JS状态时使用固定、最小、可验证的桥接协议；
- 所有扩展消息包含schema版本、长度限制以及sender、tab、origin校验；
- Manifest权限清单形成快照测试；
- 富文本、URL和动态内容采用严格安全渲染策略；
- 资格和状态接口防止通过可猜ID读取其他Owner数据；
- 状态查询有轮询上限，失败重试有速率限制；
- 采集箱分页、默认排序和超长SKU展示在真实大商品出现后实现；
- 安装交付明确侧载还是正式签名包，以及扩展ID稳定性；
- 系统时钟错误、浏览器存储被清理、扩展升级中断、磁盘配额不足和采集箱读取失败均有可诊断状态；
- 验证码测试使用安全fixture或真实偶发观察，不为了验收主动触发平台风控。

### 21.2 上线前仍需外部确认的unknown

- 1688当前服务条款、账号规则和访问频率边界；
- 真实商品详情host/path及A/B页面结构；
- 不同账号、地区、会员、代发/批发模式的价格和SKU差异；
- 供应商稳定业务身份是否能可靠取得；
- 图片CDN是否依赖Cookie、Referer或短期签名；
- Owner当前Chrome版本和是否允许侧载；
- 现有后端模型是否能表达Owner全局商品、多实验关联、多次观察和单一草稿转换。

这些unknown不能靠代码或自动测试消除。实施时应逐项取得真实环境证据，无法确认的保持unknown或阻止相应能力，不能包装成已经完成。

## 22. 2026-07-13全景调研后的产品裁决

本节吸收《1688跨境电商采集工具全景调研报告》中对官方插件、独立采集工具、跨境ERP和AI选品工具的功能归纳。报告用于发现能力类别，不直接提高任何竞品宣传数据的事实等级。

### 22.1 采用的结论

- 成熟产品的共同价值链是“页面采集 → 采集箱 → 整理与校验 → SKU/图片/成本处理 → 渠道草稿 → 经营后续”；
- 插件最适合承担页面入口、可靠抽取和即时反馈；复杂编辑、监控、成本、草稿和审批应留在凌镜系统；
- 采集价值不能只按抓取数量衡量，应按字段可靠性、部分失败可恢复、重复关系和进入后续工作的可用程度验收；
- 官方数据、页面公开声明、AI推断和Owner修改值必须分层保存。

### 22.2 暂不采信的内容

报告中的翻译准确率、采集成功率、同步秒数、违禁词拦截率等精确指标未附可复核的一手测试口径，统一标为`quoted/unknown`，不得写入凌镜验收标准。代理IP轮换、伪装UA、逆向Token/签名、规避重复铺货规则等做法不进入凌镜方案。

### 22.3 当前验收重点

1. 真实1688首页和搜索结果能识别可靠商品卡，不读取其他ERP注入内容；
2. 列表页批量结果逐项可解释、可停止、无固定数量、无自动翻页；
3. 真实详情页的阶梯价、MOQ、供应商和规格组合与Owner看到的页面一致；
4. 关键字段解析失败时阻止误导性确认保存；
5. 采集箱能够区分列表线索、详情观察、再次观察、工作副本和任务/草稿状态；
6. 一个真实列表批次和一个真实详情商品完成Chrome人工验收后，才能把对应能力从`automated_verified`提升为`manually_verified`。
