版本：v1.0  
日期：2026-06-17  
适用项目：MultiSell / 凌镜 LingMirror  
文档定位：将 `docs/aiagent/` 下的跨境电商 Agent 方案、Hermes 自进化方案和熵管理方案，收敛为一份近期可开发、可验收、可迭代的工程方案。

## 1. 背景与结论

`docs/aiagent/` 下的方案覆盖了跨境电商岗位体系、7+3 Agent 矩阵、Hermes 自进化架构、个人规则系统、熵管理系统和长期路线图。这些材料方向完整，但直接全部落地会有三个问题：

- 范围过大：A1-A7 + G1-G3 同时建设，依赖大量外部平台 API 和业务数据。
- 自动化过早：广告调价、客服回复、跨用户模式发现、自动因果归因等能力在数据未稳定前风险较高。
- 基础闭环不足：当前最需要先保证业务数据、规则、决策日志和人工反馈可信。

本开发文档给出的结论是：

```text
先做“数据可信 + 规则可信 + 决策可追溯”的 AgentOS 骨架，
再做多 Agent 协同，
最后做自进化与自净化。
```

近期主线应聚焦：

```text
A5 库存预警 + G3 折扣风控 + A6 利润监控 + G1 运营驾驶舱
```

这条链路最贴近当前项目已有能力，也最容易向真实用户证明价值。

## 3. 产品定位

第一阶段不把凌镜定义为“全自动跨境电商 AI Agent 平台”。

可信定位：

```text
凌镜 LingMirror 是面向中小跨境电商团队的 AI 运营决策与风控系统。
```

它近期要解决的问题：

- 商品、库存、物流、费用、促销、利润数据分散。
- 运营风险靠人工经验发现，容易漏掉。
- 折扣、库存、成本、广告之间缺少联动判断。
- 决策过程不可追溯，新人和 Agent 都难以复用经验。

它近期不承诺：

- 不承诺 Agent 自动完成所有运营工作。
- 不承诺跨平台自动投放广告。
- 不承诺客服自动处理复杂纠纷。
- 不承诺自学习系统自动修改核心策略。
- 不承诺跨用户协同推荐规则。

## 4. 开发原则

### 4.1 先决策闭环，后自动执行

每个 Agent 必须先完成：

```text
输入上下文 → Agent 输出 → 用户确认/修改 → 决策日志 → 规则沉淀
```

在没有足够日志和反馈前，Agent 只能建议、预警或阻断高风险操作，不能直接执行高风险动作。

### 4.2 先结构化规则，后大模型推理

库存、折扣、利润、费用这类场景优先使用确定性规则和公式。

LLM 近期只用于：

- 解释决策原因。
- 生成运营建议文案。
- 总结决策日志。
- 辅助识别规则冲突。

LLM 近期不用于：

- 直接决定是否亏损。
- 直接修改库存、价格、广告预算。
- 替代财务核算公式。

### 4.3 先个人规则，后自进化

个人规则系统近期只做显式配置和人工确认沉淀。

自动提取规则必须进入 `shadow` 或待确认状态，不能直接影响生产决策。

### 4.4 先基础熵管理，后预测式熵对抗

近期只做：

- TTL / stale 标记。
- 规则数量预算。
- 规则健康评分。
- 冲突日志。
- 人工确认合并或停用。

后置：

- TimescaleDB 遥测。
- 分布漂移检测。
- 因果归因。
- 跨用户模式发现。
- 全自动自净化闭环。

## 7. 第一阶段范围

第一阶段目标是做出一个可运行、可验收、能持续迭代的 AgentOS 骨架。

### 7.1 必须交付

#### 7.1.1 修正现有 Agent 基线

需要先修正现有不一致点：

- 后端 API 前缀实际为 `/api`，文档中不要写 `/api/v1`。
- 熵系统前端请求路径应与后端路由一致。
- 前端 Agent 路由应统一为 `/agents`、`/agents/:agentId`、`/agents/rules`、`/agents/entropy`。
- Alembic 迁移目录应写为 `backend/alembic/versions`。
- 文档引用应统一指向 `docs/aiagent/...`。

#### 7.1.2 A5 库存预警增强

A5 从示例 Agent 升级为真实业务 Agent。

输入：

- SKU。
- 当前可售库存。
- 锁定库存。
- 在途库存。
- 近 7/14/30 天销量。
- 采购提前期。
- 最小起订量。
- 目标安全库存天数。

输出：

- 库存状态：绿色、黄色、红色。
- 可售天数。
- 建议补货量。
- 建议物流方式。
- 风险原因。
- 建议操作。

验收标准：

- 任意 SKU 可计算可售天数。
- 红色预警可解释触发原因。
- 决策写入 `agent_decision`。
- 用户可提交采纳、修改、拒绝反馈。

#### 7.1.3 G3 折扣风控增强

G3 从促销检测升级为可阻断亏损风险的风控 Agent。

输入：

- SKU / ASIN。
- 成本价。
- 当前售价。
- 生效折扣列表。
- 平台。
- 最低毛利率阈值。

输出：

- 是否允许促销。
- 折后价。
- 毛利和毛利率。
- 是否低于成本。
- 是否低于最低毛利率。
- 是否存在多平台最低价风险。
- 阻断或预警理由。

验收标准：

- 折后价低于成本时必须阻断。
- 折后价低于成本价 × 1.1 时必须预警。
- 多个折扣叠加时必须模拟最终价格。
- 所有阻断和放行动作写入决策日志。

#### 7.1.4 A6 利润监控 MVP

A6 是下一阶段最重要新增 Agent。

输入：

- SKU。
- 平台。
- 国家。
- 售价。
- 采购成本。
- 包装重量和尺寸。
- 物流渠道费用。
- 平台佣金和固定费用。
- 折扣。
- 广告成本，初期可手动导入。
- 退款成本，初期可按比例估算。

输出：

- 单件预计利润。
- 预计毛利率。
- 费用拆分。
- 亏损风险。
- 毛利率异常原因。
- 调价或成本优化建议。

验收标准：

- 每个 SKU 能产出利润拆分。
- 毛利率低于阈值时预警。
- 亏损 SKU 在 G1 驾驶舱中展示。
- 用户可调整利润阈值规则。

#### 7.1.5 G1 运营驾驶舱 MVP

G1 不先做“智能经营大脑”，先做 Agent 风险汇总。

展示内容：

- 即将断货 SKU。
- 低毛利 SKU。
- 折扣风险 SKU。
- 待用户确认的 Agent 建议。
- 最近 7 天 Agent 决策数量。
- 最近 7 天用户采纳率。
- 规则健康概览。

验收标准：

- 用户打开驾驶舱即可看到今日待处理风险。
- 每条风险可以跳转到对应 Agent 决策详情。
- 页面不依赖外部平台 API 即可运行。

#### 7.1.6 决策日志闭环

每次 Agent 决策都必须写入 `agent_decision`。

最小字段：

- `user_id`
- `agent_id`
- `decision_point`
- `context_json`
- `agent_output`
- `final_decision`
- `user_action`
- `rules_applied`
- `evolution_stage`
- `confidence`
- `response_time_ms`
- `session_id`

验收标准：

- 后台能查询决策日志。
- 前端能展示 Agent 决策详情。
- 用户反馈能更新对应日志。

## 10. 个人规则系统

个人规则系统近期只做显式规则，不做未确认的自动学习。

### 10.1 规则类型

| 类型 | 用途 | 示例 |
|---|---|---|
| `veto` | 阻断操作 | 折后价低于成本时不允许促销 |
| `threshold` | 阈值控制 | 毛利率低于 15% 预警 |
| `strategy` | 策略偏好 | 库存红色时优先建议空运 |
| `style` | 文案风格 | 报告使用简洁风格 |

### 10.2 近期规则来源

允许：

- 用户手动创建。
- 系统模板初始化。
- Nudge 后用户确认创建。

不允许：

- 未经确认的自动规则直接生效。
- 跨用户推荐规则。
- 根据相似用户自动创建规则。

### 10.3 规则生命周期

近期状态：

```text
active → shadow → paused → retired
```

解释：

- `active`：正式生效。
- `shadow`：仅记录模拟结果，不影响决策。
- `paused`：用户或系统暂停。
- `retired`：过期或不再使用。

## 11. 熵管理近期落地

熵管理近期只做低成本、可解释、可人工干预的版本。

### 11.1 规则健康评分

每条规则计算健康状态：

| 维度 | 说明 |
|---|---|
| 新鲜度 | 最近是否触发 |
| 采纳率 | 触发后用户是否采纳 |
| 覆盖率 | 是否经常被用户修改 |
| 置信度 | 规则来源和历史效果 |
| 类型权重 | veto 和 threshold 权重更高 |

输出：

```text
healthy / warning / unhealthy
```

### 11.2 五道基础防线

近期实现级别：

| 防线 | 近期行为 |
|---|---|
| TTL | 长期未触发规则标记为 retired 或 shadow |
| Budget | 限制单用户、单 Agent、单决策点规则数量 |
| Decay | 长期不用的低来源优先级规则降权 |
| Merge | 只生成合并候选，不自动合并 |
| Regret | 用户多次覆盖后降级为 shadow，不自动删除 |

### 11.3 审计日志

规则状态、优先级、阈值、来源变化必须写入 `rule_mark_change`。

- 输出 ACoS 异常、预算异常、暂停建议。

交付：

- A3 Agent。
- 广告数据导入。
- 广告建议决策日志。
- 人工确认流。

### Phase 5：自进化增强

周期：6 周以后。

目标：

- Nudge 规则确认。
- Shadow Trial。
- 规则合并候选。
- 更完整的熵管理驾驶舱。

交付：

- Nudge 确认机制。
- Shadow 规则对比。
- 规则合并候选表。
- 月度规则审计报告。

## 15. 风险与控制

### 15.1 数据不准导致 Agent 不可信

控制：

- Agent 输出必须展示输入数据。
- 关键字段缺失时返回 `insufficient_data`。
- 不允许用 LLM 猜测成本、库存、平台费用。

### 15.2 自动化过早导致业务损失

控制：

- 广告、客服、价格修改默认只建议，不执行。
- 折扣低于成本只阻断，不自动修改促销。
- 自动规则必须先进入 shadow。

### 15.3 规则越来越乱

控制：

- 单用户规则总量设上限。
- 单决策点只加载 Top-N 规则。
- 长期未触发规则降级。
- 规则冲突写日志，交给用户确认。

### 15.4 方案继续发散

控制：

- 每个 Phase 必须能独立验收。
- 新 Agent 必须先说明输入、输出、数据来源、人工确认点。
- 没有真实数据源的 Agent 不进入开发。

## 16. 工程执行建议

后续实施时建议按以下顺序拆任务：

1. 修正 Agent API 和前端路由不一致。
2. 为现有 A5/G3 补真实输入样例和测试。
3. 补齐决策日志查询与反馈测试。
4. 设计 A6 利润计算服务。
5. 实现 A6 Agent。
6. 实现 G1 风险聚合 API。
7. 实现 G1 驾驶舱页面。
8. 增强规则健康评分和熵驾驶舱。
9. 再进入 A3 广告建议。

每个 Agent 开发前必须写清：

```text
agent_id
decision_points
输入字段
输出字段
规则类型
人工确认点
失败降级行为
测试样例
```

## 17. 最终路线判断

可信方案不是“立刻做完整 Hermes 自进化 Agent 系统”。

可信方案是：

```text
先把业务决策标准化，
再让 Agent 稳定参与决策，
再用规则和日志沉淀经验，
最后才让系统逐步学习和自净化。
```

近期最优开发主线：

```text
Phase 0：修正基线
Phase 1：A5/G3 增强 + 决策闭环
Phase 2：A6 利润监控
Phase 3：G1 运营驾驶舱
Phase 4：A3 广告建议
Phase 5：Nudge + Shadow + 规则健康增强
```

这条路线可以保留原始方案的长期想象力，同时避免近期开发失控。
