# 凌镜战略收缩研究：先把自己的跨境经营闭环跑通

> **历史研究，不是当前经营指令。** 本文中的“Ozon 首发市场”是假设，不再有效。当前不得预设国家、平台、类目或固定漏斗数量；执行口径以 `docs/SELF_USE_OPERATING_DIRECTION.md` 为准。

> 日期：2026-07-11
> 决策问题：凌镜应继续建设面向外部卖家的 AgentOS/SaaS/双产品，还是收缩为 Owner 自用跨境经营内部系统？
> 研究边界：只采用公司/创始人一手材料、官方案例或原始研究；仓库当前文件作为项目事实源。外部案例只证明某种路径可行，不证明凌镜必然成功。

## 结论

**推荐 A：自用真实经营闭环优先，冻结而非删除外部 SaaS 方向。**

未来 90 天，凌镜只服务一个用户（Owner）、一个经营主体、一个首发市场（Ozon）和一条结果链：候选商品 → 三选一 → 预算批准 → 上架 → 陌生客户订单 → 签收/退货观察 → 最终净利润 → 停止/换品/小幅加码。

这不是把独角兽梦想缩小，而是把“产品论证”从架构和功能数量改成不可伪造的经营证据。当前最稀缺的不是代码产能，而是需求、交易和利润反馈。继续同时建设 SaaS，会把时间投入到尚未被证明存在的外部客户问题；完全停止软件则会丢掉已形成的技术资产，也无法验证“系统是否改善经营判断”。

## 为什么现在必须收缩

### 1. 仓库已经出现战略分叉

当前仓库同时存在三种互相拉扯的口径：

- `/tmp/lingmirror-next-session-handoff.md` 已明确要求“不继续扩张双产品大教堂”，并把真实外部订单和退货后最终净利润定义为闭环。
- `TODOS.md` 仍以 `Dual-Product Cathedral — Phase 3 Activation` 开头，并列出 Evidence Warranty、Public API、Pricing、Self-Serve Onboarding 等外部产品工作。
- `DESIGN.md` 仍把产品定义为面向跨境商家与运营团队的 `B2B SaaS` 和 `AI Agent desktop application + SaaS dashboard`。
- `docs/INDEX.md` 仍把“双产品十星架构设计”标为 CEO Review 通过的当前方向。
- `docs/ROADMAP.md` 虽已强调商品决策、履约利润和安全门禁，但当前最高优先级仍是通用执行门禁与 Owner 决策台产品化，不是一个真实商品实验。
- `docs/PROJECT_STATUS.md` 记录了大量 Dev Done / Test Green；但项目病历同时承认 Agent 输出仍是 stub、MoA 仍为确定性聚合、Owner Dashboard 为 mock。工程可运行不等于经营有效。

因此，当前主要风险不是“做不出来”，而是 Agent 继续忠实执行不同的旧方向，持续增加无法产生市场证据的功能。

### 2. 自用是高质量需求发现机制，但不是外部市场证明

MIT 的 lead-user 研究把领先用户定义为：比市场多数人更早经历强烈需求、并有较高动机自行解决问题的用户。相关原始研究发现，用户经常开发后来具有商业价值的产品/流程；在 3M 的自然实验中，lead-user 项目产生的产品概念，其预测销售表现显著高于同期传统项目。[MIT 收录论文与摘要](https://web.mit.edu/people/evhippel/papers/evh-01.htm)

凌镜的 Owner 只有在**亲自持续经营跨境商品、真实承担预算和退货损失**时，才接近 lead user。仅仅“想做跨境系统”或用模拟数据操作，不构成 lead-user 证据。

同时，原始研究提醒了外推风险：NBER 关于创业实验抽样偏差的研究指出，早期用户样本代表性不足，会减少对未被代表消费者有价值的创新被商业化的机会。[NBER 原始工作论文](https://www.nber.org/papers/w28882) 这意味着自用反馈能优化 Owner 的流程，但不能自动推出“其他卖家愿意买”。

### 3. 成功案例的共同点不是“内部工具”，而是外部拉力随后出现

- Shopify 官方历史显示：创始团队先经营 Snow Devil 雪板店，因为现有电商软件不满足需要而自建工具；第一家 Shopify 店就是他们自己的店。[Shopify 官方历史](https://www.shopify.com/ca/blog/earliest-businesses)
- Basecamp 创始人 Jason Fried 说明：37signals 为解决自己设计公司的项目混乱而自建系统；真正触发产品化的是客户反复询问“这是什么，我们也能用吗”，随后外部产品收入超过设计业务才停止设计服务。[Basecamp 创始人一手叙述](https://basecamp.com/about)
- Slack 官方历史说明：Slack 起源于 Tiny Speck 为开发游戏 Glitch 而使用的内部聊天工具；游戏关闭后团队才将其开发为广泛发布的产品。[Slack 官方历史](https://slack.com/intl/en-gb/resources/why-use-slack/what-is-slack-and-how-does-it-work)

三者支持的不是“先做一个宏大内部平台”，而是：真实工作产生明确痛点 → 内部工具解决痛点 → 外部用户出现可观察拉力 → 才产品化。凌镜目前缺少的是中间两项的真实证据，而不是 SaaS 基础设施。

### 4. 过早规模化是明确的机会成本

Y Combinator 的官方创业建议要求尽快发布、做暂时不可规模化的工作，并警告在找到用户真正想要的东西之前建设支持规模化的技术和流程会浪费时间；其摘要还强调创业公司同一时间只能把一个问题解决好。[YC 官方建议](https://www.ycombinator.com/blog/ycs-essential-startup-advice/)

对凌镜而言，多租户、订阅、公共 API、外部 onboarding、跨客户数据和复杂产品包装都属于“规模化之前的基础设施”。它们可能未来有用，但现在不会回答：Owner 能否用 3,000 元以内找到一个产生最终净利润的商品？

## 三条路径比较

| 路径 | 能最快回答的核心问题 | 主要收益 | 主要风险/机会成本 | 现在的判断 |
|---|---|---|---|---|
| **A 自用闭环优先** | 系统能否改善真实选品、止损和净利润？ | 反馈真实、Owner 每天可用；保留软件长期期权；每轮实验沉淀数据 | 单一用户会造成过拟合；容易把个人习惯误认成市场需求 | **推荐**，但必须用真实交易，并设置外部解冻门槛 |
| **B 同时保留 SaaS 建设** | 同时尝试经营与软件产品化 | 表面上保留两条增长线 | 上下文切换；需要同时服务内部经营和假想客户；推迟首笔真实利润；继续制造文档冲突 | **冻结**。当前没有外部拉力，双线不是“更多机会”，而是两个未验证业务 |
| **C 停止软件、转人工经营** | 商品本身能否卖出和盈利？ | 最快接近市场，避免沉没成本继续扩大 | 无法验证系统价值；重复劳动无法沉淀；放弃已有商品、订单、成本、审批基础 | **不选作主路径**。但第一轮允许大量人工操作，软件只解决会改变判断或防止亏损的环节 |

### 推荐路径其实是 A 与 C 的严格组合

业务上采用 C 的纪律：先人工完成所有必要动作，不以“系统还没做好”为借口延迟上架。软件上采用 A 的原则：只把真实实验中反复出现、会影响决策质量或资金安全的步骤写入系统。

换言之：**不是用软件模拟经营，而是在经营中长出软件。**

## 未来 90 天的战略边界

### 唯一北极星

完成至少一轮可审计的真实商品实验，并得到“退货/争议观察期结束后的最终净利润”。销售额、下单数、AI 推荐数、页面数和 Agent 数都不是最终结果。

### 允许建设

- Ozon 候选商品证据和三选一评分；
- 全成本、最大现金风险、预算上限和停止条件；
- 真实订单状态（下单、付款、发货、签收、退款、退货、争议结束）；
- 逐笔实验账本和最终净利润；
- 高风险花钱/发布动作的 Owner 审批与审计；
- 为完成真实实验必需的平台适配或人工导入。

### 冻结建设

- 多租户、workspace 隔离扩张；
- 订阅、计费、结果收费；
- 公共 API、应用市场、自助注册和外部 onboarding；
- Evidence Warranty、跨客户知识聚合；
- 双产品品牌/信息架构和展示性 Owner Dashboard；
- 与首轮 Ozon 实验无关的新 Agent、抽象层或视觉重构。

“冻结”不是删除。已有模块保留，除非它们阻碍真实实验；但不得以未来可能需要为理由继续投入。

## 外部产品何时才能解冻

必须同时满足以下门槛，而不是由日期自动解冻：

1. **经营证据**：连续完成至少 3 轮真实商品实验，每轮都有完整成本和退货后净利润结论；至少 1 个商品达到预先定义的加码条件。
2. **内部使用证据**：Owner 连续 8 周每周使用核心闭环；系统记录的关键决策不是演示数据；至少 3 个功能被真实重复使用并明确减少损失、时间或漏记。
3. **可重复性证据**：相同流程在至少 2 个商品类目或 2 个批次复现，不依赖一次偶然爆单。
4. **外部拉力**：至少 5 位与 Owner 无利益关系的目标卖家看过真实流程；至少 3 位愿意提供自己的真实数据试用；至少 2 位愿意付费或签署有价格的试点意向。礼貌性“不错”不计。
5. **边界识别**：能明确列出哪些能力是 Owner 特有、哪些可通用；外部试点不得先触发大规模多租户重构。
6. **资金与注意力门槛**：自营实验已产生正的累计最终净利润，或软件外部试点获得真实预付款；否则不得同时开两条全速业务线。

满足后也只解冻“高接触设计伙伴试点”，不直接解冻自助 SaaS。先由 3–5 个外部卖家证明跨用户价值，再决定多租户、计费与公共 API。

## 失败模式与防护

| 失败模式 | 早期信号 | 防护 |
|---|---|---|
| 把 Owner 偏好当市场需求 | 功能很好用，但没有陌生客户交易或卖家主动询问 | 把自用证据与外部需求证据分开记账；按解冻门槛执行 |
| “开发”替代困难的经营工作 | 系统持续新增页面，上架日期不断后移 | 每个 Sprint 必须绑定一个真实实验里程碑；人工可完成时先人工 |
| 只看下单/销售额 | 订单增长但物流、广告、退款后亏损 | 只用最终净利润判定成功；观察期未结束标记为未决 |
| 内部流程过度定制 | 每个字段都只适合 Owner 当前习惯 | 前三轮允许定制；对外解冻前再做通用/特有拆分，不提前抽象 |
| 沉没成本保护 | 因已有大量模块而继续填满它们 | 存量代码不是路线图；只维护首轮实验经过的路径 |
| 双线注意力破碎 | 一周同时讨论商品利润、SaaS 定价和双产品 UI | 90 天内单一 backlog；外部想法进入冻结清单，不进入开发 |
| AI 假证据 | stub 或确定性输出被当成市场判断 | AI 只能生成假设；候选数据、订单、费用和结算必须有来源与时间戳 |

## 决策后的执行顺序

1. 将本决策写入当前方向事实源，并把双产品/SaaS 文档标为冻结历史材料。
2. 把活跃 backlog 压缩成首轮 Ozon 实验：20 个候选 → 3 个 → 1 个。
3. 先确定预算上限、不可回收损失、停止条件和最终净利润公式，再写功能。
4. 在不等待自动采集的前提下允许人工录入；用真实来源附件或链接留证。
5. 每轮结束只做一次复盘：哪项系统能力改变了决策或减少了损失？下一轮只补这一类能力。

## 最终决策句

> 凌镜当前是 Owner 自用的跨境经营内部系统，不是对外 SaaS。它的使命是用有限预算更快找到可持续盈利商品并更早止损。外部产品是被真实经营和外部付费拉力解冻的未来期权，不是并行开发任务。
