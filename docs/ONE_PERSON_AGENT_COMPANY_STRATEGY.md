# 凌镜一人 Agent 公司长期作战地图

更新时间：2026-06-29

## 1. 一句话方向

凌镜 LingMirror 的长期方向是：

```text
让一个人也能经营跨境电商公司。
```

这里的“一人”不是指所有事情都由人手动完成，而是：

```text
人负责目标、判断和关键审批；
Agent 负责观察、分析、建议、执行低风险动作和复盘结果；
系统负责可信数据、业务规则、权限、审计、平台对接和经营闭环。
```

凌镜不是普通 ERP，不是 API 拼接工具，也不是单个 AI 聊天助手。凌镜的目标是成为跨境电商 AI AgentOS。

## 2. 长期产品形态

最终系统应该有两个入口，但只有一套可信底座。

| 入口 | 使用者 | 作用 |
|---|---|---|
| 运营后台 | 运营、财务、仓库、管理员 | 维护商品、库存、订单、费用、结算、规则和基础数据 |
| AgentOS 总控台 | Owner、负责人、一人团队 | 看风险、看建议、批动作、看结果、管理 Agent |

运营后台是可信底座。AgentOS 不能绕过后台的业务规则、权限、审批和审计。

## 3. 长期战略主线

### 3.1 可信业务底座

先让系统沉淀可信事实：

- 商品
- SKU
- 供应商
- 成本
- 库存
- 价格
- 物流
- 平台费用
- Listing
- 订单
- 售后
- 结算
- 利润
- 异常
- 操作记录

没有可信数据，Agent 的建议就不可信。

### 3.2 完整经营闭环

系统不能只是一堆页面，必须围绕一条经营链路：

```text
选品
-> 商品资料
-> 成本和利润测算
-> 上架决策
-> 发布任务
-> 订单同步
-> 库存变化
-> 物流履约
-> 结算利润
-> 异常处理
-> 复盘优化
```

每次开发都要问：

```text
它让这条经营链更完整了吗？
它减少 Owner 的判断负担了吗？
```

### 3.3 Agent 岗位化

Agent 不是聊天机器人，而是业务岗位。每个 Agent 必须有清楚的职责、输入、输出、权限和风险边界。

推荐长期岗位：

| Agent 岗位 | 主要职责 |
|---|---|
| 选品 Agent | 判断候选商品是否值得进入测算 |
| 商品资料 Agent | 检查标题、规格、图片、类目、属性是否完整 |
| 物流 Agent | 计算运费、比较渠道、发现物流异常 |
| 利润 Agent | 汇总成本、费用、售价和利润率 |
| Listing Agent | 生成上架任务和发布准备 |
| 库存 Agent | 发现低库存、超卖风险和补货机会 |
| 订单 Agent | 发现履约异常、订单状态异常 |
| 售后 Agent | 分析退货、退款、争议和赔付风险 |
| 风控 Agent | 拦截价格、库存、发布、财务等高风险动作 |
| 复盘 Agent | 判断建议是否赚钱、是否减少异常、是否应调整规则 |

### 3.4 人类控制层

Owner 不应该追代码、追接口、查日志。Owner 每天应该看到：

- 今天最重要的风险是什么
- 哪些商品值得上架
- 哪些商品不建议上架
- 哪些订单、库存、利润或物流异常
- 哪些 Agent 建议需要审批
- 哪些动作已经执行
- 哪些动作失败，需要人工处理
- 哪些 Agent 判断长期有效或无效

### 3.5 平台 API 是通道，不是大脑

平台 API 的定位是：

```text
数据来源 + 受控执行通道
```

它不是系统大脑。平台 API 不能反过来定义凌镜的业务模型。

固定顺序：

```text
先统一业务模型
再接平台只读数据
最后做受控写回
```

## 4. 阶段路线

### 阶段 1：能算清楚

目标：

```text
一个商品能不能卖，系统能说清楚。
```

验收标准：

- 商品资料是否完整说得清楚
- 成本是否完整说得清楚
- 包装重量和尺寸是否完整说得清楚
- 物流费用能算
- 平台费用能算
- 利润和利润率能算
- 系统能给出建议上架或不建议上架
- 不建议上架时，原因能用业务语言解释

当前优先级：最高。

### 阶段 2：能看清楚

目标：

```text
一个人打开系统，就知道今天公司发生什么。
```

验收标准：

- 有 Owner 总控台
- 今日风险清楚
- 待审批动作清楚
- Agent 建议清楚
- 平台同步异常清楚
- 库存、订单、利润、物流异常清楚
- 每个问题都有下一步处理入口

当前优先级：高。

### 阶段 3：能接进来

目标：

```text
真实平台数据能稳定进入系统。
```

验收标准：

- 支持至少一个平台店铺授权
- 能只读同步订单
- 能只读同步商品或 Listing 状态
- 能只读同步库存或物流状态
- 能记录同步任务
- 能记录失败原因
- 能重试
- 能用业务语言告诉 Owner 失败影响

原则：

```text
先只读，不急着写回平台。
```

当前优先级：高，但不能破坏阶段 1 和阶段 2。

### 阶段 4：能建议

目标：

```text
Agent 从看数据，变成提经营建议。
```

验收标准：

- Agent 能发现商品、库存、订单、利润、物流异常
- Agent 能说明建议原因
- Agent 能说明建议影响
- Agent 能把建议变成待处理任务
- Owner 能采纳、拒绝或稍后处理
- 建议和结果都能记录

当前优先级：中高。

### 阶段 5：能受控执行

目标：

```text
低风险动作自动做，高风险动作由人审批。
```

验收标准：

- 低风险动作可自动执行并写审计
- 中风险动作进入审批
- 高风险动作默认只建议，不自动执行
- 价格、库存、订单、钱、发布、账号权限都不能绕过审批和审计
- 执行失败有状态、原因和人工处理入口

当前优先级：中。不能早于审批、审计和失败处理。

### 阶段 6：能复盘优化

目标：

```text
Agent 不只是做事，还知道做得好不好。
```

验收标准：

- 建议是否被采纳可统计
- 采纳后是否赚钱可追踪
- 哪些 Agent 经常误判可识别
- 哪些规则需要调整可提示
- 哪些动作可以提高自动化等级可评估
- Owner 能看到 Agent 贡献和风险

当前优先级：中后期。

## 5. 一人 Agent 公司成熟度

| 等级 | 名称 | 业务含义 |
|---|---|---|
| L0 | 人工公司 | 人自己做，系统只记录 |
| L1 | 工具公司 | 系统帮算成本、运费、利润和库存 |
| L2 | Agent 助理公司 | Agent 看数据、提醒、提出建议 |
| L3 | Agent 协作公司 | Agent 生成任务，人审批关键动作 |
| L4 | 半自动公司 | 低风险动作自动做，高风险动作审批 |
| L5 | 一人 Agent 公司 | 人主要定目标、看异常、批关键决策 |

当前判断：

```text
凌镜已有 L1-L2 的平台雏形，部分能力正在向 L3 发展。
下一阶段重点不是继续堆模块，而是验证经营闭环和 Owner 总控台。
```

## 6. Owner 每周只看这些问题

Owner 不需要判断技术实现。Owner 每周只看：

1. 这周系统让哪个经营链路更完整了？
2. 这周是否减少了人工判断负担？
3. 哪些动作已经能从数据变成建议？
4. 哪些建议已经能变成审批任务？
5. 哪些高风险动作仍然被系统拦住？
6. 哪些失败 Owner 能看懂并处理？
7. 哪个 Agent 更像一个可靠员工了？

如果一个功能不能回答这些问题，它就不是当前优先级。

## 7. Agent 提案强制检查表

任何 Agent 提出平台 API、AIOS、自动化、Agent、订单、库存、价格、Listing、财务相关方案，必须先回答：

| 问题 | 必须回答 |
|---|---|
| 属于哪个阶段 | 阶段 1 到阶段 6 |
| 服务哪个经营链路 | 选品、上架、订单、库存、物流、财务、售后、复盘 |
| 是读还是写 | 只读、内部写、外部平台写 |
| 是否影响高风险对象 | 价格、库存、订单、钱、发布、账号权限 |
| 是否经过统一业务模型 | 是或否 |
| 是否需要审批和审计 | 是或否，原因是什么 |
| 失败后怎么办 | 重试、人工处理、告警、回滚或阻断 |
| Owner 如何验收 | 用业务语言描述，不靠看代码 |

不回答这些问题的方案，不进入开发。

## 8. 当前不优先做什么

在阶段 1 到阶段 3 没跑稳前，不优先做：

- 同时接很多平台
- 大规模自动改价
- 自动改库存
- 自动发布商品到真实平台
- 自动处理退款、赔付或财务动作
- 只为了看起来丰富而新增页面
- 没有经营闭环的单点 Agent
- 绕过审批和审计的自动化

这些不是永远不做，而是不能早做。

## 9. 当前最应该做什么

近期推荐主线：

```text
长期方向收敛
-> 经营闭环审计
-> Owner 总控台
-> 单平台只读接入
-> Agent 建议闭环
-> 受控执行
```

第一件事：

```text
做“一人 Agent 公司闭环审计”。
```

审计目标不是看系统有多少页面，而是看一个真实经营场景能否跑通：

```text
20 个候选商品
-> 判断哪些适合上架
-> 生成上架任务
-> 看到订单、库存、利润和异常
-> Agent 提建议
-> Owner 审批关键动作
-> 系统记录结果
```

审计结果只分三类：

```text
已可用
半可用
不可用
```

## 10. 不变原则

以下原则长期不变，除非 Owner 明确接受方向变化：

1. 凌镜是 AI AgentOS，不是 API 拼接工具。
2. API 接入服务于系统，不允许 API 反过来定义系统。
3. 业务核心概念只能有一套官方模型。
4. Agent 不能直接绕过业务服务、权限、审批和审计。
5. 高风险动作默认不自动执行。
6. Owner 不需要懂技术，也必须能验收结果。
7. 所有功能最终都要回到经营闭环和一人公司目标。
