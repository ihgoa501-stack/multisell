# 两个核心业务闭环

> 为什么凌镜设计了这两个闭环，它们解决了什么问题。
> 最后更新: 2026-07-09

---

## 卖一个跨境电商商品的全过程

假设你有一个商品——从确认它可以卖，到把它卖出去，再到确认收到了钱：

1. 找到可以卖的商品（选品）
2. 确认这个商品资料完整、利润可行（分析）
3. 决定在哪个平台、以什么价格上架（决策）
4. 执行上架操作（发布）
5. 收到订单（订单来了）
6. 计算选择什么物流、多少钱（履约）
7. 收到结算款，确认赚了多少（财务）
8. 处理可能的问题退货等（售后）

凌镜把这件事分为**两个核心闭环**。

---

## 第一个闭环：商品→上架

```
候选商品 → 完整度检查 → 成本/利润测算 → 上架建议 → Owner 审批 → 受控上架 → 结果复查
```

这个闭环回答："这个商品能不能卖、赚不赚钱？要不要上架？"

### 适用场景

- 从 1688 选到了候选商品
- 供应商提供的商品需要评估是否可卖
- 需要计算完整成本（采购 + 物流 + 平台费 + 关税）
- 决定是否发布到 Ozon / Shopee

### 涉及的模块

| 步骤 | 模块 | API | 说明 |
|------|------|-----|------|
| 候选商品 | `candidate` | `POST /v1/candidates` | 选品采集入口（手动/Agent/Chrome扩展） |
| 完整度检查 | `completeness` | `POST /v1/completeness/check/:productId` | 12 维评分：标题/描述/图片/规格/价格… |
| 利润测算 | `profit` + `landedcost` + `platformfee` + `tariff` | `GET /v1/profit/summary/:productId` | 采购+物流+平台费+关税 = 到岸成本 → 利润率 |
| 上架建议 | `loop` | `POST /v1/loop/evaluate/:productId` | 全链路评估：完整度→利润→风险→建议 |
| Owner 审批 | `decision` | `POST /v1/decision/:id/approve` | 审批通过后创建 ListingTask |
| 受控上架 | `listingtask` | `POST /v1/listing-tasks/:id/publish` | 状态机：blocked→pending→executing→completed |
| 结果复查 | `listingtask` + `dashboard` | `GET /v1/listing-tasks/:id` | 发布结果和失败原因 |

### 当前实现状态

- ✅ 候选商品 CRUD（2026-06-29 MVP）
- ✅ 12 维完整度评分引擎
- ✅ 利润汇总（采购+物流+平台费+关税）
- ✅ `loop` 全链路串联
- ✅ Owner 审批 + ListingTask 状态机
- ✅ Mock 数据自动注入
- ✅ Agent A8（选品扫描）+ A12（Chrome 扩展采集）
- ⏳ 从 product-hub 创建 listing 到 Ozon/Shopee 的实际发布（需真实账号配置）
- ⏳ Agent 建议反馈回流到 A8/A12 的闭环

## 第二个闭环：订单→履约→结算

```
订单 → 库存/物流选择 → 运费测算 → 结算 → 利润核实 → 异常检测 → Agent 建议 → Owner 审批
```

这个闭环回答："已卖的订单能赚到预期的利润吗？有没有异常？"

### 适用场景

- 订单来了，需要发什么物流
- 需要确认运费预算
- 结算后要核实实际利润 vs 预期利润
- 发现异常（退货/纠纷/费用不对）

### 涉及的模块

| 步骤 | 模块 | 说明 |
|------|------|------|
| 订单 | `order` + `orderimport` | 订单管理 + CSV 批量导入 |
| 物流选择 | `logistics` (A10) | 四类定价模式（first_additional / tiered / fixed / per_kg），YAML 费率表 |
| 运费测算 | `shipping` | 承运商 + 渠道报价 |
| 结算 | `settlement` | 结算单管理 + 对账 |
| 利润核实 | `finance` + `allocation` | 财务总览 + 成本分摊 |
| 异常检测 | `aftersales` + `exceptions` | 退货分析 + 异常中心 |
| Agent 建议 | `entropy` + `evolution` + `trustscore` | 自净化评分 + 自主权门控 |

### 当前实现状态

- ✅ 订单管理 + CSV 批量导入
- ✅ 物流 A10 费率引擎（四种定价模式、YAML 配置）
- ✅ 承运商 + 渠道报价
- ✅ 平台费用规则
- ✅ 结算管理 + 对账（含 reconciliation）
- ✅ 财务总览 + 利润计算
- ✅ 成本分摊
- ✅ 售后管理 + 退货追踪
- ⏳ Settlement 自动对账（目前需手动触发 reconcile）
- ⏳ 库存-物流联动（订单确认后自动选择最优物流）
- ⏳ A6 ProfitWatch Agent 实时利润监控（当前为定时 1h 扫描）

## 为什么是两个闭环，不是一个

凌镜的设计是渐进可信：**先让商品闭环可信，再让履约闭环可信。**

如果把所有东西都串成一个大循环，有两个问题：

1. **调试困难**：出问题了你不知道是选品错了、还是物流算错了、还是平台费配错了
2. **Owner 不可控**：一个错误会波及下游所有步骤

两个闭环的边界在这里：

```
         ┌──── 第一个闭环 (上架前) ──────────────────┐
         │  候选商品 → 完整度 → 利润 → 审批 → 上架   │
         └──────────────────┬───────────────────────┘
                            │ 上架后，商品上架状态变更
                            ▼
         ┌──── 第二个闭环 (上架后) ──────────────────┐
         │  订单 → 物流 → 结算 → 利润核实 → 异常    │
         └──────────────────────────────────────────┘
```

第一个闭环在本地产生"可信的商品建议"。第二个闭环验证"实际的经营效果"。

---

## 不在闭环中的常见问题

| 操作 | 为什么不在闭环中 | 归属于哪里 |
|------|-----------------|-----------|
| 纯 CRUD 商品管理 | 没有"决策"环节，是基础设施 | `sku` / `brand` / `category` 模块 |
| 汇率管理 | 是实时数据，不是闭环步骤 | `exchangerate` 模块 |
| 全局搜索 | 是工具不是流程 | `search` 模块 |
| RBAC 权限管理 | 基础设施，不是业务操作 | Platform Kernel |
| AI 生图 (Prism) | 商品内容的辅助工具 | `imagegen` 模块 |
| Dashboard | 数据展示窗口 | `dashboard` 模块 |
