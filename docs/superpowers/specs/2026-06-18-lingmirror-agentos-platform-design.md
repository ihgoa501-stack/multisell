# LingMirror AgentOS Platform Design

Date: 2026-06-18
Status: Draft approved through brainstorming

## 1. Product Positioning

LingMirror is not a generic Agent builder, and it is not a traditional ERP dashboard. The target product is:

> A cross-border e-commerce specific AI AgentOS platform: a template-driven, auditable, controllable AI-native commerce workspace.

The system should help sellers move from "manually operating pages" to "setting business goals, reviewing Agent work, approving risky actions, and auditing outcomes."

The first version should not compete with Dify, n8n, Make, or Zapier as a general-purpose workflow canvas. LingMirror should win through cross-border e-commerce depth: Listing, product selection, inventory, logistics, platform fees, profit, compliance, approval, and audit.

## 2. Design Inputs

The design references the current LingMirror codebase and product research documents:

- Existing backend AgentOS capabilities: 10 registered Agents, 4-stage autonomy model, decisions, rules, Agent actions, entropy defenses, SPC, and audit models.
- Existing frontend modules: dashboard, Agent dashboard, Agent list/detail/rules, actions, entropy cockpit, products, listings, inventory, orders, settlement, finance, exceptions, notifications, and operation logs.
- Research on AI-native workspaces: TRAE Work, QoderWork, WorkBuddy, desktop Agent patterns, cloud-edge execution, skills, MCP, Human-in-the-Loop, and remote approval.
- Competitive analysis of AI Agent platforms: Dify, Coze, n8n, Zapier Agents, Make, Relevance AI, and the market gap for cross-border e-commerce specific Agent templates.

## 3. Core Product Decisions

### 3.1 Engineering Skeleton

The first version uses an AgentOS shell rather than a big-bang full automation rollout.

The shared workflow is:

```text
Business event -> Agent observation -> Decision/task -> Human-in-the-loop -> Execution -> Review/learning
```

All Agents should produce auditable decisions and, when an action is possible, a controllable work item.

### 3.2 Product Language

Agents are organized as three business squads:

| Squad | Agents | Responsibility |
|---|---|---|
| Growth Squad | A1 product scouting, A2 Listing optimization, A3 advertising advice | Product discovery, content, traffic, and listing quality |
| Fulfillment Squad | A5 inventory, G2 warehouse/customs, order/logistics Agent | Stock, order, warehouse, customs, shipping, and fulfillment closure |
| Risk Squad | A6 profit, A7 compliance, G3 discount risk | Profit protection, compliance, discounts, platform red lines |

This gives the product an AI team model while preserving the existing Agent IDs and backend structure.

### 3.3 Work Modes

LingMirror should expose three user-facing modes:

| Mode | Meaning | First-Version Behavior |
|---|---|---|
| Ask | Query and explanation | Read-only business analysis and answers |
| Agent | Collaborative execution | Agent creates suggestions, tasks, and approvals |
| Quest | Delegated workflow | User sets a goal; Agent runs a bounded workflow and interrupts on risk |

Phase 1 can implement the modes as product semantics and UI entry points. Full Quest automation can deepen later.

## 4. Home Page: AgentOS Control Center

The home page should become an AI workbench, not a traditional metric dashboard.

First screen layout:

1. Top: business health summary
   - Today's sales/profit
   - Inventory risk
   - Pending approvals
   - Agent automation rate

2. Left: task source and status filters
   - All tasks
   - Growth Squad
   - Fulfillment Squad
   - Risk Squad
   - Product listing, inventory, orders, profit, customer service, compliance
   - Pending, running, completed, blocked

3. Center: AI task workbench
   - Work item cards with context, Agent recommendation, expected benefit, risk, and audit trail
   - Actions: approve, modify, assign, ignore, inspect audit

4. Right: Agent team status and autonomy controls
   - Squad health
   - Adoption rate
   - Pending approvals
   - Red-line blocks
   - Agents eligible for promotion/demotion
   - Emergency pause

5. Lower page: audit, template recommendations, scheduled reports

The user's daily workflow should start from tasks and approvals generated by the AI team, not from manually visiting every business module.

## 5. Navigation Structure

Recommended primary navigation:

1. AgentOS Control Center
2. Task Center
3. Agent Squads
4. Templates and Skills
5. Business Data
6. Audit and Safety
7. System Settings

Existing modules should be retained but repositioned:

| New Area | Existing Capabilities |
|---|---|
| AgentOS Control Center | Current dashboard + Agent dashboard, reorganized around tasks |
| Task Center | AgentActions, Exceptions, Notifications, pending decisions |
| Agent Squads | AgentList, AgentDetail, AgentRules, EntropyCockpit |
| Templates and Skills | Pre-listing decision, Listing optimization, inventory replenishment, profit risk, customer service drafts |
| Business Data | Products, SKUs, categories, brands, suppliers, logistics, platform fees, inventory, orders, settlement, finance |
| Audit and Safety | Operation logs, RBAC, entropy management, safety red lines, AI usage records |

The left navigation should avoid exposing dozens of flat modules. Business data pages remain available, but they are no longer the primary daily entry point.

## 6. Unified WorkItem Model

The product should introduce a unified WorkItem concept. It can initially be a frontend/API view model rather than a new database table.

Possible sources:

- AgentDecision
- AgentAction
- ExceptionItem
- Notification

Minimum fields:

| Field | Purpose |
|---|---|
| source_type/source_id | Links back to the original technical object |
| business_object | Product, SKU, order, listing, settlement, platform, etc. |
| squad/agent_id | Shows the responsible Agent team |
| title/summary | Human-readable task |
| context | Key business facts used by the Agent |
| recommendation | Agent proposed action |
| risk_level | Low, medium, high, critical |
| approval_required | Whether user approval is mandatory |
| status | Pending, running, approved, rejected, executed, blocked |
| audit_link | Links to decision, action, operation log, and rule changes |

The user should see one task language, not multiple backend object types.

## 7. Autonomy, Safety, and Approval

LingMirror's autonomy model should remain aligned with the current backend stages:

| User Label | Backend Stage | Behavior |
|---|---|---|
| Observation | OBSERVATION | Read data, generate reports, no recommendation or action |
| Suggestion | SUGGESTION | Generate suggestions; user executes |
| Semi-autonomous | SEMI_AUTONOMOUS | Low-risk actions can execute; high-risk actions require approval |
| Full autonomous | FULL_AUTONOMOUS | Bounded routine execution; exceptions interrupt the user |

Each Agent decision point should be configurable independently. For example, A5 inventory alerts can be semi-autonomous while A5 logistics choice remains suggestion-only.

### 7.1 Trust Score

Trust Score should be visible in the Agent Squad and autonomy panels. Suggested components:

- Adoption rate: 40%
- Mean confidence: 25%
- Rule consistency: 20%
- Stability/SPC: 15%

Phase 1 may use simplified computed thresholds and existing decision history. A full scoring engine can be implemented in a later iteration if needed.

### 7.2 Safety Red Lines

Red lines override every autonomy level.

Default red-line classes:

- Amount-based: purchasing, price change, advertising budget, refunds over threshold
- Batch-based: actions affecting more than a configured number of SKUs/orders/platforms
- Irreversible: delete product/listing, change bank account, tax, platform auth, or credentials
- First-time action: first publish to a platform, first use of a template, first action type for an Agent

Red-line triggers should create an approval work item and write an audit record.

### 7.3 Emergency Controls

The product needs visible emergency controls:

- Pause all Agents
- Downgrade one Agent
- Disable one rule
- Force fallback to Observation when LLM or tool execution is unstable

## 8. Templates and Skills

Phase 1 should provide built-in cross-border e-commerce templates, not an open-ended workflow canvas.

P0/P1 template candidates:

- Listing optimization
- Product selection analysis
- Pre-listing profitability decision
- Inventory replenishment
- Profit risk monitoring
- Customer service draft
- Compliance detection
- Discount risk review

Long-term, successful workflows should become reusable skills. A Skill should represent a structured, auditable business workflow, not only a prompt.

Phase 1 should not include:

- Open Skill marketplace
- General low-code canvas
- User-created arbitrary Agent tools

## 9. Cloud, Desktop, and IM Strategy

Phase 1 should use Web as the primary surface.

Long-term surface split:

| Surface | Role |
|---|---|
| Web | Main control center, approvals, data views, audit, templates |
| Desktop | Local files, Excel/CSV, images, browser automation, sensitive local execution |
| IM/mobile | Remote dispatch, approval, alerts, daily reports |

Cloud-edge strategy:

- Cloud/Web first for business data, decisions, audit, approvals, fees, and platform rules.
- Future desktop/local execution for sensitive local files, large spreadsheets, media assets, and browser automation.

## 10. MVP Scope

### 10.1 Phase 1: Deep Implementation

Phase 1 should deeply implement:

- AgentOS Control Center
- Unified Task Center and WorkItem view
- Agent Squad pages
- Autonomy overview and basic control
- Approval queue and safety red lines
- AI usage/audit records
- Product pre-listing decision flow
- Inventory and profit warnings
- Built-in template entry points

### 10.2 Phase 1: Shallow Entry Points

Phase 1 should include light entry points for:

- Advertising: suggestions/drafts only, no automatic ad spend changes
- Customer service: reply drafts only, no automatic real customer replies
- Compliance: detection and warnings only, no automatic platform submissions
- IM: notification/approval entry point only, no full two-way workflow
- Skills: built-in templates only, no marketplace

### 10.3 Later Phases

Phase 2:

- Deeper product selection, advertising, customer service, and compliance Agents
- Scheduled task engine
- IM approval and report delivery
- Trust Score automation and promotion nudges

Phase 3:

- Desktop client/local execution
- Browser automation
- Skill marketplace
- Custom Agent templates
- Dynamic model routing
- Deeper external platform API execution
- Team/enterprise governance

## 11. Non-Goals

The first version explicitly does not:

- Build a general Agent platform for all industries
- Compete with Dify/n8n as a general developer tool
- Expose a complex low-code canvas
- Ship a complete desktop client
- Open a plugin or Skill marketplace
- Fully automate high-risk business actions by default
- Deeply integrate every marketplace API

## 12. Success Criteria

The first usable AgentOS version is successful if:

- Users understand LingMirror as an AI operating team, not just an ERP.
- Daily work starts from Control Center and Task Center.
- At least one deep business chain works from business event to Agent decision, approval, execution, and audit.
- High-risk Agent actions are consistently blocked or routed to approval.
- Agent autonomy is visible and controllable.
- Existing business data pages remain usable as context and manual editing surfaces.
