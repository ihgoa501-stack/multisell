# 1688 采集插件 L3 验收合同

> 状态：当前发布门禁
> 范围：Owner 浏览器配对 → 1688 详情/首页/列表采集 → 私人采集箱定位 → 重复处理与重启恢复
> 证据边界：页面字段最高为 `quoted`；采集成功不证明供应商、价格、SKU、库存或图片权利真实。

## 1. L3 的完成定义

L3 不是“页面出现按钮”或“单元测试通过”。只有下面两个门禁都通过，才可标记 `manually_verified`：

1. **自动化门禁**：版本、安全边界、配对、解析、重复、对账和采集箱代码合同通过；
2. **真实 Chrome 门禁**：同一个 Owner 在正式目标环境完成配对、详情采集、列表采集、记录定位、重复选择和浏览器重启恢复，并保存请求与结果证据。

任一门禁失败时，插件状态只能写 `implemented` 或 `automated_verified`，不能写“生产可用”。

## 2. 自动化门禁

在仓库根目录执行：

```bash
./scripts/verify_1688_plugin_l3.sh
```

脚本失败即停止发布。它执行：

- manifest、package、lock、详情解析器、列表解析器和后端接受版本的一致性检查；
- Chrome 扩展全部测试（含配对来源、详情/列表 DOM、重复选择、请求对账和恢复）；
- `/settings/plugin` 与 `/sourcing1688` 聚焦前端测试；
- `internal/auth` 与 `internal/domain/sourcing1688` 后端测试。

自动化通过仍不能替代真实 Chrome 门禁。

## 3. 真实 Chrome 门禁

### 3.1 验收前置

- [ ] 正式服务器源码提交、后端镜像标签、前端镜像标签和目标提交一致；禁止复用旧标签重建镜像。
- [ ] 正式数据库迁移为该提交要求的最新版本，`dirty=false`。
- [ ] `CORS_ALLOWED_ORIGINS` 等于当前凌镜网页 Origin，不得使用 `unused.invalid`、`*` 或测试地址。
- [ ] Chrome 加载的未打包扩展路径和本次构建目录一致，扩展版本等于 manifest 版本。
- [ ] 记录测试时间、提交 SHA、扩展 ID、扩展版本和目标环境；不得记录密码、JWT 或 device secret。

### 3.2 安全配对

1. 登录凌镜并打开 `/settings/plugin`。
2. 点击“连接1688采集助手”。8 秒内必须出现当前浏览器、设备编号、插件编号、生产/验收环境和唯一权限说明。
3. 点击“确认连接”，页面“已经连接的浏览器”必须出现同一设备。
4. 关闭并重新打开 Chrome，再打开插件；设备仍能刷新短期凭证，不要求再次输入凌镜账号密码。
5. 在扩展存储中确认：网页登录 JWT 不存在；只允许设备凭据和短期 extension token。
6. 从凌镜断开设备后，再次采集必须被拒绝且不保存。

通过证据：配对前后截图、设备 ID（可遮盖中段）、确认后的设备列表、重启时间、撤销后的 401/中文提示。
失败条件：原始 `HTTP 401/403`、无限等待、要求复制网页登录 Token、错误环境仍可写入。

### 3.3 详情页单商品采集

1. 打开一个真实 `https://detail.1688.com/offer/{id}.html` 商品页并等待 SKU 区稳定。
2. 点击“采集到凌镜”，预览必须显示标题、价格、MOQ、供应商、SKU 数、图片数以及缺失/解析失败项。
3. 确认保存后必须显示 `request_id` 对应的正整数 `record_id`；不得只显示“成功”。
4. 点击“查看采集记录”，必须打开 `/sourcing1688?record_id={同一ID}`，并自动定位同一条 `unverified_lead`。
5. 采集箱中的标题、原链接、采集时间和页面预览逐项核对；差异保留为 unknown/parse_failed，不得补造。

通过证据：1688 URL、预览截图、`request_id`、`record_id`、采集箱定位截图。
失败条件：静默保存、record ID 不一致、打开错误记录、SKU 解析失败却声称完整。

### 3.4 首页/搜索列表采集

1. 分别在 1688 首页或搜索页选择当前可见商品；全选只能选中当前页面已识别卡片。
2. 执行批量采集，结果必须逐项显示 saved、duplicate、failed 或 stopped，不能只报一个总成功数。
3. 中途点击停止；尚未发送的商品不得继续写入。
4. 浮层拖动后不得遮挡页面主要操作；刷新列表页后仍可再次正常选择。
5. 从结果中的任一 `record_id` 打开采集箱，必须定位对应记录。

通过证据：选中数、实际发送数、逐项结果、停止前后时间、抽查的 record ID。
失败条件：采集隐藏/未选商品、停止后继续写、失败被计为成功、无法定位记录。

### 3.5 重复商品

1. 再次采集 3.3 中的同一 offer。
2. 必须显示本次与已有观察在标题、价格、MOQ、供应商、SKU 数、图片数和观察时间上的对比。
3. 未选择前不得覆盖已有记录。
4. “查看已有记录”打开原 `record_id`；“保存为新观察”沿用同一商品记录并新增不可变快照/观察次数。

通过证据：重复提示、两种选择各一次、原 record ID、新 snapshot ID/观察次数。
失败条件：静默覆盖、生成无法关联的新商品、没有明确选择也保存。

### 3.6 断网与浏览器重启恢复

1. 在提交后、结果返回前制造断网或关闭 Chrome。
2. 重开 Chrome 和插件后，不得盲目重复 POST；插件必须按原 `request_id` 查询保存结果。
3. 终态只能是：已保存并给出 record ID、服务器明确未保存、仍需对账。`404` 不能直接解释为未保存。
4. `reconcile_required` 时再次重启仍保留待对账提示，不允许用户误以为可安全重复采集。

通过证据：原 request ID、重启时间、恢复查询、最终状态和 record ID（如已保存）。
失败条件：重启丢失、自动重复写、把未知结果显示为失败或成功。

### 3.7 错误文案与失败关闭

至少人工触发并核对：凌镜登录失效、插件未安装/未响应、1688 未登录、风控/验证码、非商品页、商品下架、页面加载中、SKU 未稳定、网络断开、设备已撤销。

每条提示必须包含：发生了什么、商品是否保存、Owner 下一步做什么。不得直接展示 `HTTP 403`、堆栈、JWT 或内部数据库错误。

## 5. 当前自动化覆盖与仍需人工验证

现有自动化已覆盖：受信配对 Origin、设备凭据刷新、详情与列表 DOM 解析、页面异常识别、重复选择、request 对账、恢复历史、record ID 响应解析、采集箱 `record_id` 查询参数和中文配对错误提示。

真实 Chrome 仍必须验证：content script 实际注入、网页桥到 service worker 的消息、扩展 Origin/CORS、真实 1688 DOM 变化、首页/搜索懒加载、按钮与浮层遮挡、浏览器休眠/重启、生产网络中断、真实数据库记录定位。上述项目不能由 jsdom、fixture 或 mock fetch 宣称通过。
